**Highlights**:
- **Two-axis wallet model (PR #107)** — Before this change, `WalletType` enum encoded both key derivation (HD vs SingleKey) and key availability (local vs watch-only vs remote). An interim attempt added `WatchOnly` / `Remote` cases that conflated the axes — the smell showed up in `DefaultWalletProvider.GetAddressProviderAsync`, which had to *recover* the derivation by sniffing the descriptor string (`tr(pubkey)` vs `*`). The capability-on-provider rework reverted `WalletType` to `SingleKey | HD` only, made `ArkWalletInfo.Secret` nullable (and `ArkWalletEntity.Wallet` nullable, with `.HasFilter("\"Wallet\" IS NOT NULL")` on the unique index so SQL Server allows multiple null-Wallet rows — harmless on Postgres / SQLite which already treat `NULL` as distinct under a unique index), and pushed the capability resolution down to `IWalletProvider.GetSignerAsync`. The dispatch is now: `Secret`-present → local signer; `Secret` null + `IRemoteSignerTransport.KnowsWalletAsync(walletId)` returns `true` → remote-signed; else `null` → watch-only. Address provider dispatches purely on `WalletType` — no descriptor sniffing. `WalletFactory.CreateWatchOnlyWallet(accountDescriptor, …)` infers `WalletType` from the descriptor's wildcard at creation time (one place, not at every address-provider call). `TransactionHelpers` (3 sites — checkpoint sign / batch sign / forfeit sign) and `TreeSignerSession` (2 sites) hoist the null-signer check above their per-VTXO loops so a watch-only wallet surfaces a descriptive `InvalidOperationException` before any signing work starts (forfeit path message specifically calls out that watch-only wallets can't participate in batches demanding a forfeit — the reviewer's most protocol-sensitive finding). Sample wallet `Backup.razor` renders an explicit "no backup required" branch for null-Secret wallets so it doesn't show an empty mnemonic grid. All 404 existing tests pass.
- **MuSig2 secret nonce stays inside the signer (PR #113)** — The previous `IArkadeWalletSigner` / `IRemoteSignerTransport` contracts returned `MusigPrivNonce` from `GenerateNonces` and required callers to pass it back into `SignMusig`. That made the secret nonce cross the signer boundary — for the remote-signer transport that meant the "remote signer" wasn't actually one (secret material round-tripped over the wire), and for in-process signers it encouraged callers to hold MuSig2 secrets in their own data structures where accidental reuse leaks the private key (MuSig2 nonce reuse is catastrophic). Reshaped contract: `GenerateNonces(descriptor, context, sessionId)` returns `MusigPubNonce` only — the signing source derives the secret nonce internally and stores it in a per-instance `ConcurrentDictionary<string, MusigPrivNonce>` keyed by `sessionId`. `SignMusig(descriptor, context, sessionId)` drops the `MusigPrivNonce` parameter and `TryRemove`s the secret on consume so the store self-evicts on the happy path. `GenerateNonces` throws if a nonce is already stored for the same `sessionId` (double-call without intervening `SignMusig` would orphan secret material — almost certainly a caller bug; in-process signers now check `ContainsKey` **before** generating to avoid burning entropy on a duplicate-`sessionId` collision). `sessionId` is caller-supplied because `MusigContext.AggregatePubKey` isn't unique per signing operation — in a batch tree, multiple transactions can share cosigner set + taproot tweak so their `AggregatePubKey`s are identical even when sighashes differ (the sighash is internal to `MusigContext` and not externally observable); `TreeSignerSession` passes each tree-node txid. `TreeSignerSession._myNonces` collapsed from `Dictionary<uint256, (MusigPrivNonce, MusigPubNonce)>` to `Dictionary<uint256, MusigPubNonce>` — the secret half no longer round-trips through the batch coordinator. `IRemoteSignerTransport` `<remarks>` notes long-lived transports need an eviction policy (TTL or bounded count) for abandoned nonces — in-process signers get away with remove-on-consume because their lifetime is the batch session, but a server-side transport could leak unconsumed entries if a client generates a nonce and never signs. `DefaultWalletProvider` caches signer instances per wallet so the in-process nonce store survives between `GenerateNonces` and the matching `SignMusig` — a fresh signer per call would silently break MuSig2 signing (the second call would always find an empty store and throw).
- **Compose signers from `IDescriptorSigningSource`s (PR #114)** — Pushed signer composition down one layer: an `IArkadeWalletSigner` is now always a `CompositeArkadeWalletSigner` built from one or more `IDescriptorSigningSource`s. Each source answers `CanProvideAsync(descriptor)` and exposes the signing operations rooted in the key it owns; the composite dispatches each call to the first source that claims the descriptor. The three previous concrete signers collapse into sources behind the same composite: `Bip39SigningSource` (was `HierarchicalDeterministicWalletSigner`; claim by master fingerprint match on the descriptor's origin), `NsecSigningSource` (was `NSecWalletSigner`; claim by x-only pubkey match on `tr()` descriptors — `NsecSigningSource.FromNsec` mirrors the old `NSecWalletSigner.FromNsec` static), `RemoteTransportSigningSource` (was `RemoteArkadeWalletSigner`; claim by `IRemoteSignerTransport.KnowsWalletAsync`; passthrough proxy). The three old concrete signer classes were **deleted** since they're equivalent to a `CompositeArkadeWalletSigner` over the matching single source; the public `IArkadeWalletSigner` interface didn't move, so call sites compile unchanged. `IDescriptorSigningSource` is **operation-level** (`Sign` / `SignMusig` / `GenerateNonces` / `GetPubKey`) rather than returning a raw `ECPrivKey` — that's load-bearing for the remote case: a remote source can implement the contract honestly without round-tripping secret material over the wire. The original sketch in issue #112 returned `ECPrivKey` and would have defeated remote signing — flagged in review and corrected. `DefaultWalletProvider.GetSignerAsync` cache key collapsed from `(walletId + secret hash + transport)` to `wallet.Id` alone (re-import is an out-of-band event handled by host restart or explicit cache invalidation — documented in the field comment). Cache check moved above source construction so the hot batch-participation path (called per-VTXO) skips `Bip39SigningSource` construction (which derives the master fingerprint via the static `ExtKey` cache — in-process overhead is small but matters once a remote transport's `KnowsWalletAsync` is a network call). Each local source keeps its own per-session `ConcurrentDictionary` nonce store with the sessionId-keyed semantics established in PR #113. The earlier "hybrid (local + remote on the same wallet)" claim was dropped from README + wallets.md: `RemoteTransportSigningSource.CanProvideAsync` delegates to `KnowsWalletAsync`, which is wallet-grained, not descriptor-grained, so "local view-path + remote spend-path" isn't actually expressible without a per-descriptor probe on the transport — filed as follow-up, meanwhile docs only promise what the current contract delivers.
