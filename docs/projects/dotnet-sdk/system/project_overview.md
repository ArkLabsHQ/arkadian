# NArk (.NET Ark SDK) -- Project Overview

## What is NArk?

NArk is a .NET SDK for building Ark protocol wallets and applications. It provides the complete client-side stack for interacting with an Ark Service Provider (arkd) -- including VTXO lifecycle management, batch round participation with MuSig2 tree signing, intent-based off-chain transactions, coin selection, on-chain sweeping/recovery, and Boltz atomic swaps (ARK<->BTC).

The SDK is published as NuGet packages and designed to integrate into any .NET application via dependency injection and the `IHostBuilder` pattern.

## NuGet Packages

| Package | Purpose |
|---------|---------|
| **NArk.Abstractions** | Interfaces, models, contracts, vendored NBitcoin.Scripting (OutputDescriptor, parser, SigningRepository), `ArkBip21` builder + parser |
| **NArk.Core** | All services, gRPC + REST transport, batch sessions, scripts, wallet, coin selection, pending-tx recovery, `NArk.Core.Payments.LnurlHelper` (LNURL-pay decode + Lightning-address resolve + callback invoice fetch — lifted from the WASM sample in PR #106 so downstream hosts no longer copy-paste it) |
| **NArk.Swaps** | Multi-provider swap architecture (`ISwapProvider` abstraction + `BoltzSwapProvider`), VHTLC, MuSig2 cross-signatures, PaymentTrackingService (`IHostedService`) |
| **NArk.Storage.EfCore** | Entity Framework Core storage (VTXOs, contracts, intents, wallets, swaps, payments, payment requests; opt-in `ConfigureArkExitEntities()` adds unilateral-exit tables; opt-in `ArkStorageOptions.StoreDateTimeOffsetAsTicks` lets SQLite consumers `ORDER BY` `DateTimeOffset` columns) |
| **NArk** | Meta-package aggregating Core + Swaps |

## Core Features

1. **VTXO Management** -- Track, poll, and synchronize VTXOs across wallets with active script monitoring
2. **Batch Session Participation** -- Join arkd batch rounds: register intents, exchange MuSig2 nonces, sign VTXO trees, submit forfeit transactions
3. **Intent System** -- Create, register, synchronize, and schedule Ark intents for off-chain transactions
4. **Coin Selection** -- Automatic coin selection with dust threshold handling and sub-dust OP_RETURN support
5. **Taproot Contracts** -- Payment contracts, note contracts, hash-locked contracts, VHTLC contracts with Tapscript leaf trees
6. **On-Chain Operations** -- Boarding (on-chain to off-chain), settlement, and collaborative exit
7. **Sweeping** -- Automated recovery of expired and swept VTXOs on-chain
8. **Multi-Provider Swaps** -- ARK-to-BTC and BTC-to-ARK chain swaps, submarine, and reverse swaps via a pluggable `ISwapProvider` interface. `SwapsManagementService` is a provider-agnostic router; `BoltzSwapProvider` is the shipped Boltz implementation (websocket monitoring, status polling, cooperative refunds for submarine + both chain-swap directions, MuSig2 claiming, chain-swap renegotiation on `transaction.lockupFailed`, 10-consecutive-404 safety net). Providers expose capability metadata via `SwapRoute` / `SwapAsset` / `SwapNetwork` / `SwapQuote` / `SwapLimits` and raise `SwapStatusChanged` for status transitions
9. **HD Wallets + Two-axis Wallet Model** -- Hierarchical deterministic address derivation with descriptor recycling, plus gap-limit recovery (`HdWalletRecoveryService`) that rebuilds local contract state after mnemonic re-import via pluggable `IContractDiscoveryProvider`s (indexer-VTXO, boarding-UTXO, Boltz-swap, plus custom sources). **PR #107** introduced the orthogonal two-axis model: `WalletType` (`HD | SingleKey`) controls key derivation, while signing capability is answered by `IWalletProvider.GetSignerAsync` — `ArkWalletInfo.Secret` is nullable, so the same data shape covers HD or SingleKey × local / watch-only / remote-signed. `WalletFactory.CreateWatchOnlyWallet(descriptor, …)` infers `WalletType` from the descriptor's wildcard at creation time so the address-provider path never has to sniff the descriptor string
10. **Caching Transport** -- gRPC + REST clients with response caching for server info
11. **Payment Tracking** -- ArkPayment / ArkPaymentRequest domain models with `PaymentTrackingService` (`IHostedService` lifecycle, subscribe in `StartAsync` / unsubscribe in `StopAsync`) that auto-updates statuses from VTXO/intent/swap events. Asset tracking via `ArkPayment.Assets` and `ArkPaymentRequest.ExpectedAsset` / `ReceivedAssets` (JSONB-persisted, accumulated via `MergeAssets`). Explicit `Cancelled` status distinct from `Failed`. `SemaphoreSlim` serialises `OnVtxoChanged` so concurrent VTXOs at the same payment request don't race read-compute-write on `ReceivedAmount`. Opt-in via `AddArkPaymentTracking()`
12. **Output Descriptor Support** -- Vendored NBitcoin.Scripting (OutputDescriptor, PubKeyProvider, parser combinators, SigningRepository) shipped in `NArk.Abstractions/Scripting/` for descriptor-based wallet integrations
13. **Server-driven Limits** -- VTXO/UTXO amount bounds, `max_tx_weight`, and `max_op_return_outputs` are read from `GetInfo` and enforced client-side in `SpendingService`, `BoardingUtxoSyncService`, and `DefaultCoinSelector`
14. **Resilient VTXO Sync** -- `VtxoSynchronizationService` keeps **one long-lived arkd `GetSubscription` stream** open and mutates the watched script set **in place** (PR #103). A supervisor loop owns the stream; when a contract appears or disappears, the service issues `SubscribeForScriptsAsync(added, _subscriptionId)` / `UnsubscribeForScriptsAsync(_subscriptionId, removed)` deltas — no stream teardown / recreate (the teardown window was exactly when a pushed event could slip through). The supervisor reconnects on the same subscription id, recreates it if arkd reports it GC'd (TTL after a disconnect), and tears it down when the active set is empty. The 5-second safety-net poll **re-derives the active script set fresh from `IActiveScriptsProvider`s every tick** (PR #102, replacing the cached `_lastViewOfScripts` that desynced when `ActiveScriptsChanged` was lost) and reconciles the stream subscription to it, so a stale or missed subscription can never hide a script — the next tick re-derives, polls, and reconciles. `GatherActiveScriptsAsync` isolates per-provider failures so one storage hiccup can't blank the set. Each stream push still enqueues a **single immediate poll** (PR #99 dropped the prior 750 ms / 3 s / 8 s retry schedule). A persistent **per-wallet `vtxo.lastFullPollAt` cursor** (stored via `ArkWalletEntity.Metadata`) bounds the cold-start catch-up window across process restarts; a gate flag prevents a failed catch-up + successful routine poll from advancing the cursor past the gap.
15. **Per-wallet Wallet Metadata** -- `ArkWalletInfo.Metadata` (JSON-serialized dictionary on `ArkWalletEntity`) lets the SDK accumulate per-wallet bookkeeping (sync cursors, recovery state, etc.) without per-concern column-add migrations. `IWalletStorage.SetMetadataValue(walletId, key, value, ct)` performs sparse-key updates (`value=null` removes; concurrent writers on different keys don't clobber each other)
16. **Boltz Referral Attribution** -- `BoltzClientOptions.ReferralId` (default `"arkade-dotnet-sdk"`, exposed as `BoltzClientOptions.DefaultReferralId`) is stamped on every Submarine / Reverse / Chain swap-create request so Boltz can attribute swaps to the originating integration. Consumer apps with their own referrals (BTCPay's `"btcpay-arkade"`, wallet's `"arkade-money"`) override via `services.Configure<BoltzClientOptions>`; setting it to `null` opts out
17. **Persistent Boltz Websocket** -- `SwapsManagementService` now keeps a single long-lived Boltz websocket connection (5 s reconnect backoff, re-subscribes from the watch set) and uses subscribe / unsubscribe ops keyed by swap id, matching the documented Boltz API model. Replaces the per-swap-set-change reconnect that violated the websocket protocol
18. **Chain-Time Cache & Fallback** -- `RPCChainTimeProvider` caches `(Timestamp, Height)` on every successful call and falls back to the cache (with a Warning log) on transient Bitcoin Core RPC failures, so a single 500 from `getblockchaininfo` no longer forces controller-bound consumers (e.g. BTCPay's plugin manager) to disable the plugin. Cold-start failures still throw
19. **Per-wallet Log Scopes** -- Public per-wallet entry points across Swaps, Batch, Onchain, Intent, Spending, Asset, Recovery, Delegation, and Sweeper services open `BeginScope(("WalletId", id))` so downstream sinks can route every transitively-emitted log line to the right wallet
20. **Pending Arkade Transaction Recovery** -- `PendingArkTransactionRecoveryService` reconciles off-chain txs stranded between `SubmitTx` and `FinalizeTx` (process crashed after the server locked the inputs in-flight). Runs on host startup via `ArkHostedLifecycle` across every wallet, plus on-demand `FinalizePendingArkTransactionsAsync(walletId)` for per-wallet recovery (e.g. immediately after user unlock). Builds a BIP-322 ownership proof anchored on each batch's first VTXO (uses spent VTXOs as proof material too), calls the new `IClientTransport.GetPendingTxAsync` endpoint, signs the returned checkpoint PSBTs, and finalizes them. Per-tx failures raise `RecoveryFailed` (`PendingTxRecoveryFailureEventArgs`) without blocking the loop; the next host start retries any unfinalized leftovers. Mirrors the recovery loop pattern in go-sdk and ts-sdk
21. **BIP21 / Payment-string Parser** -- `ArkBip21` builder + parser handles BIP21 URIs, Ark addresses, BOLT11 invoices, LNURL, and Bitcoin addresses into a unified `Bip21PaymentInfo` with `PreferredMethod` routing (`ArkSend` / `SubmarineSwap` / `ChainSwap`). Uses `System.Uri` + `HttpUtility.ParseQueryString`; amounts stored as decimal BTC with `AmountSats` derivation; `Parse` (lenient) vs `ParseStrict` modes. Builder supports `WithAssetId()` and `WithCustomParameter()`. **PR #109**: `Build()` requires at least one destination from `{arkAddress, onchainAddress, lightning}` (asset alone is a what-to-send constraint, not a destination — does not satisfy the precondition). Lightning-only and asset-only URIs emit the empty-address form (`bitcoin:?lightning=…` or `bitcoin:?asset=…`) so receive screens that drop the Ark / on-chain path while keeping Lightning keep the QR scheme stable across toggle states
22. **Swap Recovery Inspection** -- `InspectSwapRecoveryAsync(walletId, swapId)` returns a read-only `SwapRecoveryInfo` snapshot (refreshes the local VTXO cache from arkd for the swap's contract script before reporting) with `SwapRecoveryStatus` of `Recoverable` / `NoFunds` / `AlreadyRefunded` / `AlreadySettled` / `StillPending` / `SwapNotFound` / `InspectionError`. `ScanRecoverableSwapsAsync(walletId)` is the bulk version (O(N) sequential arkd round-trip — not for hot UI paths). Side-effect-free: recovery itself happens inside `BoltzSwapProvider.PollSwapState` on the next routine poll once a swap reaches a refundable Boltz status — these are purely for UI/audit reporting
23. **Unilateral Exit** -- `UnilateralExitService` orchestrates the full exit pipeline when arkd is unavailable or uncooperative. State machine (`Broadcasting` → `AwaitingCsvDelay` → `Claimable` → `Claiming` → `Completed`) driven by `StartExitAsync(walletId, vtxoOutpoint, claimAddress)` + `ProgressExitsAsync()`. Idempotent re-invocation; `ExitWatchtowerService` auto-starts exits on owned VTXOs whose ancestors hit the chain. Backed by `VirtualTxService` (fetches and stores the whole tx chain from arkd's `GetVtxoChainAsync` + `GetVirtualTxsAsync`, tagging each row with `ChainedTxType` — `Commitment` / `Tree` / `Ark` / `Checkpoint` / `Unspecified`) and `P2ACpfpBuilder` (v3 1p1c CPFP package relay via the new `IFeeWallet` abstraction; gracefully falls back to direct broadcast when no fee wallet is registered). Wired by `AddUnilateralExit()`. **Storage modes**: (a) EF Core via opt-in `ConfigureArkExitEntities()` — adds `ExitSessionEntity` / `VirtualTxEntity` / `VtxoBranchEntity` to the model; (b) in-memory via `AddInMemoryExitStorage()` — same code paths, no schema; (c) stateless one-shot API (`BroadcastExitChainAsync` → `ExitPlan` record + `ClaimMaturedExitAsync(ExitPlan)`) — caller owns persistence in whatever form they want (JSON blob, settings entry, file on disk). **Fetch modes**: `VirtualTxOptions.DefaultMode` defaults to `Lite` (txids + expiry only, hex fetched on demand at `StartExitAsync`); set to `Full` for strict offline-exit requirements (stores raw tx hex at every VTXO arrival). **Auto-fetch**: opt-in `AddVirtualTxAutoFetch()` registers `VtxoChainAutoFetchService` (listens to `IVtxoStorage.VtxosChanged` and pre-stores chains for every new VTXO above the configured worth-threshold). Prune-on-spend (`PostSpendVirtualTxPruneHandler`) stays auto-wired regardless
24. **Unified Blockchain Interface** -- `IBitcoinBlockchain` (six members: `GetChainTime`, `GetUtxosAsync`, `BroadcastAsync`, `BroadcastPackageAsync`, `GetTxStatusAsync`, `EstimateFeeRateAsync`) replaces the prior split `IBoardingUtxoProvider` / `IChainTimeProvider` / `IOnchainBroadcaster` trio that were always wired from the same backend client. Three concrete impls under `NArk.Core/Blockchain/`: `NBXplorerBlockchain` (preserves cached-fallback chain-time on transient RPC failures + `submitpackage` with sequential-fallback for Core ≥28), `EsploraBlockchain` (sequential-broadcast fallback — no `txs/package` endpoint), `RpcBlockchain` (chain time + broadcast + tx status; `GetUtxosAsync` throws `NotSupportedException` — no native address index). DI helpers `AddNBXplorerBlockchain` / `AddEsploraBlockchain` / `AddRpcBlockchain` register every interface a backend supports; `ArkApplicationBuilder.WithBlockchain<T>()` replaces the prior `WithTimeProvider<T>()`
25. **Deterministic Asset Packets** -- `AssetPacketBuilder.Build` emits `AssetGroup` entries in a stable `(AssetId, GroupIndex)` ordinal-hex order regardless of input order or internal `HashSet` enumeration, so the same logical asset transfer always serializes to identical OP_RETURN bytes across runs. Matches the canonical ordering in rust-sdk's `(txid, groupIndex)` sort, making packets reproducible and **byte-exactly comparable against ts-sdk / rust-sdk fixtures**. Cross-SDK conformance is now enforced by a fixture suite under `NArk.Tests/Assets/Fixtures/` (`asset_ref`, `asset_input`, `asset_output`, `metadata` — including the `MetadataList` Merkle-hash vectors) imported verbatim from `arkade-os/ts-sdk@master`
26. **Network Endpoint Defaults (Esplora + Electrum)** -- `ArkNetworkConfig` now ships nullable defaults for `EsploraUri`, `ElectrumWsUri`, and `ElectrumTcpUri` (`tcp://host:port`) on every preset, mirroring the canonical Arkade ts-sdk's `WS_DEFAULT_URLS` / `ESPLORA_URL` / `ELECTRUM_TCP_HOST`. Lets apps wire `IBitcoinBlockchain` (Esplora flavor) straight off the preset (`services.AddEsploraBlockchain(new Uri(ArkNetworkConfig.Mainnet.EsploraUri!))`) without their own NBXplorer / bitcoind. Per-network values: Mainnet `https://mempool.arkade.sh/api` / `wss://electrum.arkade.sh` / `tcp://electrum.arkade.sh:50001`; Mutinynet `https://mempool.mutinynet.arkade.sh/api` / `wss://electrum.mutinynet.arkade.sh` / `tcp://electrum.mutinynet.arkade.sh:50001`; Regtest `http://localhost:3000` / `ws://localhost:50003` / `tcp://localhost:50000`. Electrum TCP ports verified at the `server.version` protocol level against the public Fulcrum hosts — only `:50001` plain-TCP is exposed on Mainnet / Mutinynet (TLS goes via the WSS endpoint at `:443`); Regtest uses nigiri's electrs binary port `:50000` (`:30000` is the HTTP REST endpoint, a different protocol). Additive nullable fields appended to the positional record — existing named-args callers are untouched. JSON keys: `esplora`, `electrum-ws`, `electrum-tcp`
27. **Unconfirmed Boarding-UTXO Filter** -- arkd's `validateBoardingInput` rejects unconfirmed boarding inputs at settle time, so offering them as spendable coins is misleading and any spend built from one is doomed. `ArkVtxo.IsUnconfirmedOnchain()` reads a shared `ArkVtxo.ConfirmedMetadataKey = "Confirmed"` metadata flag (populated by `BoardingUtxoSyncService` from the explorer's confirmation status — any value other than `"True"` case-insensitive means unconfirmed). `SpendingService.GetAvailableCoins` filters these VTXOs out and logs the skip count at Debug. The helper is **confirmation-centric rather than boarding-specific**: today only boarding sync populates the flag, but arkd-reported unrolled VTXOs generalise for free once they carry it. Off-chain tree VTXOs that lack the key return `false`. The Blazor sample wallet (`samples/NArk.Wallet/.../Pages/Vtxos.razor`) surfaces the state as a **PENDING** pill. Documented in `README.md` and `docs/articles/spending.md` (PR #101).

28. **LNURL-Pay Helper (SDK Surface)** -- `NArk.Core.Payments.LnurlHelper` (PR #106) decodes `lnurl1…` bech32 strings, resolves Lightning Addresses (`user@domain`) into LUD-06 / LUD-16 pay-params, and fetches BOLT11 invoices from the LNURL callback URL — all without Ark-specific state. Public surface: `IsLnurl(input)`, `DecodeLnurl(input)`, `ResolveAsync(input, ct)` → `LnurlPayParams`, `FetchInvoiceAsync(callback, amountSats, ct)`. Detection rules pin: bech32 `lnurl1…`, `lightning:` scheme prefix, Lightning Address (`user@domain`), and rejection of plain on-chain strings and leading-`@`. Callback wire format covers millisat conversion, `?`/`&` separator handling, and surfacing the server `error` field. Lifted out of the WASM sample so downstream wallet hosts (e.g. WalletWasabi) consume the SDK type via `using NArk.Core.Payments;` instead of copy-pasting or maintaining a parallel version. Public API unchanged from the sample version; `CancellationToken` parameters added for SDK-style consistency. No new dependencies — uses NBitcoin's bech32 encoder + `System.Net.Http.Json`.

29. **Watch-Only and Remote-Signed Wallets** -- Same data shape as a local-key wallet (`Secret = null` on `ArkWalletInfo`); the runtime distinction is decided by `IWalletProvider.GetSignerAsync` (PR #107). No `IRemoteSignerTransport` registered (or `KnowsWalletAsync(walletId)` returns `false`) → watch-only: address derivation and VTXO observation work, signing-dependent paths throw a descriptive `InvalidOperationException` hoisted above the per-VTXO loops in `TreeSignerSession` and `TransactionHelpers` (forfeit-sign path message specifically notes watch-only wallets can't participate in batches demanding a forfeit). Transport registered and claims the wallet → remote-signed: `GetSignerAsync` returns a `CompositeArkadeWalletSigner` wrapping `RemoteTransportSigningSource`; every signing call is forwarded to the transport with `walletId` so one transport instance serves many wallets. `IRemoteSignerTransport` is an *optional* constructor dependency on `DefaultWalletProvider` — apps that don't use remote signing don't have to register one. EF Core: `ArkWalletEntity.Wallet` column is nullable; the unique index gets `.HasFilter("\"Wallet\" IS NOT NULL")` so SQL Server allows multiple null-Wallet rows (Postgres / SQLite already treat NULL as distinct under a unique index). Sample wallet (`samples/NArk.Wallet/.../Pages/Backup.razor`) renders an explicit "no backup required" branch for null-Secret wallets so it doesn't show an empty mnemonic grid.

30. **Composed Signer (IDescriptorSigningSource)** -- `IArkadeWalletSigner` is always a `CompositeArkadeWalletSigner` built from one or more `IDescriptorSigningSource`s (PR #114). Each source answers `CanProvideAsync(descriptor)` and exposes operation-level signing methods rooted in the key it owns — *never* returning `ECPrivKey`, which is what lets a remote source implement the contract honestly without round-tripping secret material. The composite dispatches each call to the first source that claims the descriptor; order matters (local sources get first refusal in `DefaultWalletProvider`, remote is fallback). Three sources ship: `Bip39SigningSource` (claims by descriptor origin's master fingerprint), `NsecSigningSource` (claims by descriptor's x-only pubkey; `NsecSigningSource.FromNsec(...)` is the renamed `NSecWalletSigner.FromNsec` entry point), `RemoteTransportSigningSource` (claims via `IRemoteSignerTransport.KnowsWalletAsync`). The three previous concrete signers (`HierarchicalDeterministicWalletSigner`, `NSecWalletSigner`, `RemoteArkadeWalletSigner`) were deleted in PR #114 — existing call sites compile because the `IArkadeWalletSigner` interface didn't move. Each local source carries its own per-session `ConcurrentDictionary<string, MusigPrivNonce>` nonce store (see Core Feature 31).

31. **MuSig2 Nonce Stays Inside the Signer** -- PR #113 reshaped the signer contract so the MuSig2 secret nonce never crosses the signer boundary. `GenerateNonces(descriptor, context, sessionId)` now returns `MusigPubNonce` only — the signing source derives the secret internally and stashes it in a per-instance `ConcurrentDictionary<string, MusigPrivNonce>` keyed by `sessionId`. `SignMusig(descriptor, context, sessionId)` drops the `MusigPrivNonce` parameter and `TryRemove`s the secret on consume so the store self-evicts on the happy path. `GenerateNonces` throws if a nonce is already stored for the same `sessionId` (calling twice without an intervening `SignMusig` would orphan secret material — almost certainly a caller bug). `sessionId` is caller-supplied because `MusigContext.AggregatePubKey` isn't unique per signing operation — multiple tree-tx nodes can share cosigner set + tweak so their `AggregatePubKey`s are identical even when sighashes differ; `TreeSignerSession` passes each tree-node txid. `TreeSignerSession._myNonces` collapsed to `Dictionary<uint256, MusigPubNonce>` so the secret half no longer round-trips through the batch coordinator. `IRemoteSignerTransport` `<remarks>` block documents that long-lived transports need an eviction policy (TTL or bounded count) for abandoned nonces. `DefaultWalletProvider` caches signer instances per `wallet.Id` so the in-process nonce store survives between the `GenerateNonces` call and the matching `SignMusig` call — a fresh signer per call would silently break MuSig2 signing (PR #114 collapsed the cache key from `(walletId + secret hash + transport)` to `wallet.Id` alone after re-import was clarified as an out-of-band event handled by host restart, and moved the cache-hit short-circuit above source construction so the hot batch path avoids per-VTXO master-fingerprint derivation + `KnowsWalletAsync` round-trips).

32. **Unified Wallet Recovery (`IWalletRecoveryService`)** -- PR #104 added a wallet-type-agnostic recovery facade in `NArk.Swaps` (the layer that can see both Core recovery services and the swap services). One `RecoverAsync(walletId, options?, ct)` call rebuilds everything reconstructable for a wallet imported into empty storage — contracts (incl. legacy script variants under deprecated server signers), the HD derivation index, funds (VTXOs), boltz swap data, and any in-flight Arkade transactions. Dispatches by `WalletType`: **HD** → `HdWalletRecoveryService.ScanAsync` does a gap-limit index scan that probes the indexer / boarding / boltz providers (the boltz provider restores swaps in-line); **SingleKey** → `EnsureSingleKeyContractAsync` derives the one deterministic default contract if storage is empty (no index to scan), then `SwapsManagementService.RestoreSwaps` runs against the wallet's account descriptor directly (throws if `AccountDescriptor` is null — fail-fast, not silent-skip). Both paths then run `PendingArkTransactionRecoveryService.FinalizePendingArkTransactionsAsync(walletId)` to finalize stranded in-flight Arkade txs, poll the indexer via `VtxoSynchronizationService.PollScriptsForVtxos` for every recovered offchain (non-boarding) script so balances repopulate deterministically, and call `SwapsManagementService.ScanRecoverableSwapsAsync` to audit the post-recovery state of every known swap. Returns `WalletRecoveryReport(WalletType, HdScan?, ContractsRecovered, RestoredSwaps, SwapAudit, FinalizedPendingTxIds, FundsScriptsSynced)` where `ContractsRecovered` is the **delta** newly persisted by this run (not the total in storage — a rescan on a populated wallet may discover nothing new). `IndexerVtxoDiscoveryProvider` simultaneously upgraded to probe the cross-product `{ current signer ∪ DeprecatedSigners } × { current exit delay ∪ mainnet-legacy 7-day delay (605184s, mainnet only) }` × `{ default contract ∪ ArkDelegateContract per RecoveryDelegateConfig.Delegates entry }` in **one indexer query**, so funds locked under a rotated/legacy server key, the historical mainnet exit delay, or a delegate descriptor are found alongside the current-signer default. Deprecated x-only signers' descriptors are reconstructed via the new `KeyExtensions.ToOutputDescriptor(ECXOnlyPubKey, Network)` extension. Server-info caching reshaped to hold the result (with a `SemaphoreSlim` first-fetch lock) instead of a `Lazy<Task>` so a transient arkd hiccup mid-scan doesn't poison every later probe into a silent zero-result recovery. Registered as a singleton by `AddArkSwapServices`. Documented in the README's new "Wallet Recovery" section.

## Relationship to Other Ark Projects

- **arkd** -- NArk connects to arkd via gRPC (or REST + SSE) as its Ark Service Provider (uses ark/v1 proto definitions)
- **go-sdk** -- Go equivalent of this SDK; NArk implements the same protocol concepts (intents, batch sessions, VTXOs)
- **fulmine** -- NArk's E2E stack uses fulmine as the Boltz-side Ark wallet for swap testing
- **Boltz** -- NArk.Swaps integrates with Boltz for atomic ARK<->BTC chain swaps and BOLT11 submarine / reverse swaps
- **wallet** -- Browser wallet; NArk serves the same purpose for .NET applications, plus a Blazor WASM sample wallet at `samples/NArk.Wallet/` published to GitHub Pages alongside the DocFX docs site
- **arkade-regtest** -- Shared regtest environment (added as a `regtest/` git submodule) replaces the previous bespoke `NArk.Tests.End2End/Infrastructure/` for E2E and local development
