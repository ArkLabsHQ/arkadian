# NArk (.NET Ark SDK) -- Architecture

## Solution Structure

The solution (`NArk.sln`) contains 9 projects organized in a layered architecture:

```
NArk.Abstractions  ← Interfaces, models, zero service logic
       ↑
NArk.Core          ← Services, transport, batch sessions, wallet, scripts
       ↑                    ↑
NArk.Swaps         NArk.Storage.EfCore
       ↑
NArk               ← Meta-package (bundles Core + Swaps for consumers)

NArk.AppHost              ← .NET Aspire orchestrator for E2E test infrastructure
NArk.Tests                ← Unit tests (NUnit + NSubstitute)
NArk.Tests.End2End        ← Integration tests using Aspire-hosted services
NArk.Transport.GrpcClient.Tests ← Transport-specific tests
NArk.Scratchpad           ← Development scratch area
```

### NArk.Core (depends on Abstractions)
- gRPC transport (`GrpcClientTransport` → `IClientTransport`); `IClientTransport.GetPendingTxAsync` surfaces server-side pending Arkade txs gated by a BIP-322 ownership proof. Chain-introspection methods `GetVtxoChainAsync`, `GetVirtualTxsAsync`, `GetVtxoTreeAsync` (and their REST equivalents in `RestClient/RestClientTransport.Exit.cs`) power the unilateral-exit pipeline. **`GetVtxoChainAsync` is now intent-authenticated + paginated (PR #158)**: the signature gained optional `string? intentProof, string? intentMessage` parameters — when supplied (a BIP-322-style ownership proof), the call authenticates against the Arkade indexer so servers with **withheld/private tx exposure** return the chain (and the fully-signed virtual txs) instead of stripping it; the proof is presented on the first page and the server returns an auth token that transparently drives opaque cursor pagination for the rest. Omitting the proof keeps the legacy anonymous outpoint lookup (public-exposure servers only). **Chains are ordered leaf → root** (the VTXO's own tx first, ending at the on-chain Commitment anchor) — the `VtxoChainEntry` and `GetVtxoChainAsync` doc comments were corrected to match arkd's actual order (PR #154). **VTXO subscription on arkd's unified `GetSubscription` API (PR #148, replacing PR #103's primitives)**: `OpenSubscriptionStreamAsync(initialScripts, existingSubscriptionId)` opens the long-lived server stream and yields `VtxoSubscriptionEvent`s — `VtxoSubscriptionStarted(SubscriptionId)` first on a new subscription (id assigned server-side), then `VtxoScriptsChanged(Scripts)` on each push; `UpdateSubscriptionScriptsAsync(subscriptionId, add, remove)` mutates the watched set in place via arkd's `UpdateSubscription` RPC (no-op when both deltas are empty). The old `SubscribeForScriptsAsync` / `UnsubscribeForScriptsAsync` / `GetVtxoSubscriptionStreamAsync` / `GetVtxoToPollAsStream` surface was removed. `VtxoSynchronizationService` consumes the new API to keep one stream open and update the watched set in place rather than restarting
- Caching decorator (`CachingClientTransport`)
- Services: `SpendingService`, `CoinService`, `ContractService`, `SweeperService`, `OnchainService`, `IntentGenerationService`, `IntentSynchronizationService`, `VtxoSynchronizationService`, `BatchManagementService` (PR #118 — on `StreamStartedEvent` now reconciles by re-subscribing every active intent's topics so an intent that reached `WaitingForBatch` during the stream-connect window — when the prior `UpdateTopicsAsync` silently skipped on a null `_streamId` — doesn't get stuck unsubscribed and re-proposed every batch round forever; `UpdateStreamTopics` add is idempotent so the reconcile is safe), `PendingArkTransactionRecoveryService`, `UnilateralExitService`, `OnchainSweepService` (PR #147 — `SweepExpiredUtxosAsync` now fully builds, signs, and broadcasts the CSV unilateral-exit sweep tx; previously a `NotImplementedException` stub. Takes `IClientTransport` + `IBitcoinBlockchain`: parses the `ArkBoardingContract`, spends the expired VTXO via its `UnilateralPath()` tapscript at the contract's CSV `Timeout`, sends to a freshly-derived boarding address, signs the taproot script-path with the wallet signer, broadcasts via `IBitcoinBlockchain.BroadcastAsync`; throws if the VTXO isn't a boarding contract or the wallet has no signer), `VirtualTxService`, `ExitWatchtowerService` (+ `ExitWatchtowerBackgroundService`), `VtxoChainAutoFetchService`, `VtxoChainProofProvider` (PR #158 — `IVtxoChainProofProvider`; builds the BIP-322 `{"type":"get-data"}` ownership proof that authenticates `GetVtxoChainAsync` against the indexer for a VTXO the wallet owns, returning `null` when the VTXO is untracked / its contract can't be resolved / no signer is registered so callers fall back to the anonymous lookup; registered singleton in `AddArkCoreServices`, injected into the services that fetch VTXO chains). **PR #154** reworked the exit services: `UnilateralExitService` and `ExitWatchtowerService` now identify the chain **leaf by txid-match against the VTXO's own outpoint** and the **root by `ChainedTxType.Commitment`** — by identity, not array position — because `GetVtxoChainAsync` returns the chain leaf-first (the old `branch[0]==root` assumption pointed CSV checks and claim-tx building at the wrong row); `UnilateralExitService` also broadcasts **one not-yet-onchain link per call** (root→storage-reverse order, BIP 431 TRUC 1-descendant rule) and broadcasts a preconfirmed VTXO's script-path checkpoint + Arkade-tx links, not just settled VTXOs' key-path tree txs
- Blockchain (`NArk.Core/Blockchain/`): `NBXplorerBlockchain`, `EsploraBlockchain`, `RpcBlockchain` — concrete `IBitcoinBlockchain` impls that collapsed the previous split `IBoardingUtxoProvider` + `IChainTimeProvider` + `IOnchainBroadcaster` trio. RPC impl throws `NotSupportedException` on `GetUtxosAsync` (no native address index — pair with NBX/Esplora for boarding-UTXO discovery). `NBXplorerBlockchain.BroadcastPackageAsync` passes `maxfeerate=0` (unlimited) + `maxburnamount=21e6` to `submitpackage` so Ark P2A anchor outputs (non-zero value, non-standard SegWit v1 script) aren't rejected by Bitcoin Core's default `maxburnamount=0` burn-output check (PR #117); the sequential fallback broadcasts the CPFP parent via the new direct-RPC `BroadcastRpcAsync` (`sendrawtransaction` with the same `maxburnamount` override) because NBXplorer's HTTP broadcast endpoint doesn't expose that parameter. **PR #154** hardened two paths that stalled unilateral exit: `GetTxStatusAsync` resolves the confirmation height via a `getblockheader` call on the returned `blockhash` (Bitcoin Core's `getrawtransaction` has no `blockheight` field — the old code left `BlockHeight` permanently null, so the CSV-maturity check never advanced), and `BroadcastPackageAsync` now inspects `submitpackage`'s `package_msg` + per-tx `tx-results[*].error` and returns failure with a Warning log when any package tx is rejected (`submitpackage` returns RPC success even on rejection, which had caused an infinite re-broadcast loop)
- Exit pipeline (`NArk.Core/Exit/`, `NArk.Core/VirtualTxs/`): `P2ACpfpBuilder` (v3 1p1c CPFP children for TRUC tree-tx relay; takes `IFeeWallet` for sighash-callback signing — never holds raw keys); `InMemoryExitSessionStorage` + `InMemoryVirtualTxStorage` (`ConcurrentDictionary`-backed alternatives to the EF Core storages, wired via `AddInMemoryExitStorage()`); **`VirtualTxFinalizer`** (PR #154 — static class ported from arkd's `redeem.go` / `finalizer.go`: `Parse(hex, network)` assembles each PSBT input's witness — aggregated key-path sig, or an Arkade script-path witness — into a broadcastable `Transaction`, and `IsBroadcastReady(hex)` predicate reports whether a stored copy is fully signed so `VirtualTxService`'s self-healing capture only freezes a branch once it's broadcast-ready and never clobbers a sig-less template served right after a batch; shared by the exit broadcast and the online-capture paths so a settled VTXO exits from storage with zero operator refetches)
- Events: `PostSpendVirtualTxPruneHandler` (auto-wired prune-on-spend, serializable transaction for `PruneForSpentVtxoAsync` race)
- Batch: `BatchSession`, `TreeSignerSession`, `TreeValidator`, `TxTree`. CSV-spend tx construction is centralized in `TransactionHelpers.BuildCsvSpendTransaction` (PR #147 — extracted from `UnilateralExitService`, now shared with `OnchainSweepService`). Forfeit-tx construction in `TransactionHelpers` now sets input sequences to match arkd's `tree.BuildForfeitTx` exactly (PR #141 / #146): the VTXO input uses `0xFFFFFFFE` when the forfeit closure carries a CLTV (non-final, so nLockTime applies) and `0xFFFFFFFF` otherwise, and the connector input is pinned to `0xFFFFFFFF` (NBitcoin would otherwise default it to `FeeSnipping` 0xFFFFFFFE under a non-zero nLockTime) — a mismatch diverges the txid and arkd rejects with `INVALID_FORFEIT_TXS`. `TransactionHelpers.ConstructArkTransaction` applies the same locktime discipline to the **ark tx** itself (PR #161): a checkpoint's collaborative leaf preserves the original VTXO leaf's CLTV, so arkd's `offchain.buildArkTx` re-derives the ark tx's `nLockTime` (max absolute locktime across inputs) and a non-final input sequence (`cltvSequence = 0xFFFFFFFE`) from that closure when it rebuilds the tx to verify the client's txid. When any checkpoint coin carries a non-zero `LockTime`, the ark tx now sets `LockTime` to the max across inputs and adds each coin with `Sequence = 0xFFFFFFFE` (mirroring arkd/ts-sdk `buildVirtualTx`), and rejects a mix of seconds/blocks absolute locktimes (a single `nLockTime` field can't encode both). Non-CLTV spends keep the plain `AddCoins` path (locktime 0, final sequences) — a no-op. Before this the checkpoint tx got the locktime but the ark tx was built with a plain `AddCoins`, so a CLTV spend's ark tx txid diverged from arkd's rebuild → `ARK_TX_MISMATCH` (checkpoint txids already agreed), surfacing on the covenant refund path (a hashlock/non-CLTV path was unaffected)
- Wallet: `DefaultWalletProvider`, `HierarchicalDeterministicAddressProvider` (canonical HD derivation via `GetDescriptorFromIndex`; PR #153 cleaned up the provider logic — an unknown-purpose derivation now yields an `ArkPaymentContract` like the HD path rather than an HTLC with a random preimage, and dead code was removed), `SingleKeyAddressProvider`, `WalletFactory` (`CreateWallet` for HD / SingleKey; `CreateWatchOnlyWallet(accountDescriptor, …)` infers `WalletType` from the descriptor's wildcard at creation time so the address-provider path doesn't have to sniff the descriptor at every call), `CompositeArkadeWalletSigner` (only `IArkadeWalletSigner` impl; aggregates `IDescriptorSigningSource`s), `SigningSources/Bip39SigningSource` + `SigningSources/NsecSigningSource` + `SigningSources/RemoteTransportSigningSource` (PR #114 — the three concrete signers `HierarchicalDeterministicWalletSigner` / `NSecWalletSigner` / `RemoteArkadeWalletSigner` were deleted in favour of composition behind the same composite). `DefaultWalletProvider.GetSignerAsync` dispatches **cache check first** (PR #114 perf — avoids per-VTXO master-fingerprint derivation + `KnowsWalletAsync` round-trips on the hot batch path) then on miss: `Secret`-present → local source (`Bip39SigningSource` for HD, `NsecSigningSource` for SingleKey); `IRemoteSignerTransport.KnowsWalletAsync` claims it → adds `RemoteTransportSigningSource`; otherwise `null` (true watch-only). Signer cache key is `wallet.Id` alone — re-import is an out-of-band event handled by host restart
- Recovery: `HdWalletRecoveryService` (sweeps derivation indices, dedupes by script, persists with `Source=recovery:<provider>`, monotonically bumps `wallet.LastUsedIndex`, probes providers in parallel per index via `Task.WhenAll`, treats throwing providers as not-found), `IndexerVtxoDiscoveryProvider` (arkd indexer probe; PR #104 upgraded it to probe the **cross-product** `{ current signer ∪ DeprecatedSigners } × { current exit delay ∪ mainnet-legacy 7-day delay (605184s, mainnet-only) }` × `{ default ArkPaymentContract ∪ ArkDelegateContract per RecoveryDelegateConfig.Delegates entry }` in a single `GetVtxoByScriptsAsSnapshot` query, mapping back to the owning contract by `scriptPubKey` hex; server-info caching reshaped from `Lazy<Task<ArkServerInfo>>` to a result-cache + `SemaphoreSlim` first-fetch lock so a transient arkd failure mid-scan no longer poisons every later probe into a silent zero-result), `BoardingUtxoDiscoveryProvider` (NBXplorer/Esplora probe on `ArkBoardingContract` on-chain address; conditional registration), `NullContractDiscoveryProvider` (no-op fallback filtered out by orchestrator)
- Scripts: `CollaborativePathArkTapScript`, `UnilateralPathArkTapScript`, `NofNMultisigTapScript`, `HashLockTapScript`, `LockTimeTapScript`
- CoinSelector (`NArk.Core/CoinSelector/`): `ICoinSelector` — `SelectCoins` final parameter changed from `int? maxInputs` to `long? maxInputWeightWu` (PR #145). `DefaultCoinSelector` (DI default, greedy) accumulates `ArkTxWeightEstimator.GetInputWeightUnits` per added input and throws `TooManyInputsException` when the budget is exhausted before the target is covered. Both `DefaultCoinSelector` and `EARSCoinSelector` now drop **unrolled** coins (`.Where(c => !c.Unrolled)`) up-front (PR #154 — an unrolled VTXO's funds are on-chain and can't be spent off-chain, so they were only ever producing doomed txs). `EARS/` subtree (PR #124) is the alternative expiry-aware selector: `EARSCoinSelector` + `CoinSelectionEngine` driving `ExpiryFirstStrategy` / `RgliStrategy` / `SingleRandomDrawStrategy` / `BranchAndBoundStrategy` over expiry-windowed `ExpiryBucket`s, scoring by lowest `Waste` (`change + inputCount × CostPerInputSats`), reserving asset-bearing coins first; tunable via `CoinSelectionPolicy`

Required for cross-SDK fixture stability against ts-sdk / rust-sdk and for reproducible packets across runs
- Payments (`NArk.Core/Payments/`): `LnurlHelper` (lifted from `samples/NArk.Wallet/` in PR #106) — `IsLnurl` / `DecodeLnurl` / `ResolveAsync` / `FetchInvoiceAsync` + `LnurlPayParams`. - Events: `PostBatchSessionEvent`, `PostCoinSpendEvent`, `PostSweepActionEvent`, `PostIntentSubmissionEvent`
- Hosting: `ArkApplicationBuilder`, `ServiceCollectionExtensions`

### NArk.Swaps (depends on Core)
- `Abstractions/ISwapProvider` -- Pluggable swap-provider interface (`ProviderId`, `DisplayName`, `SupportsRoute`, `GetAvailableRoutesAsync`, `StartAsync`/`StopAsync`, `GetLimitsAsync`, `GetQuoteAsync`, `SwapStatusChanged`, default no-op `NotifyVtxoChanged`/`NotifySwapChanged` hooks). Drives the multi-provider router; new providers participate by overriding only the hooks they care about.
- `Abstractions/SwapRoute` + `SwapAsset` + `SwapNetwork` + `SwapQuote` + `SwapLimits` + `SwapStatusChangedEvent` -- Capability-discovery models. `SwapAsset` covers BTC across Arkade / Lightning / on-chain (EVM scaffolding stripped from this PR — reserved for a follow-up LendaSwap provider).
- `SwapsManagementService` -- Provider-agnostic router over `IEnumerable<ISwapProvider>`. The existing public API (Initiate* / PayExisting* / Restore*) remains as backward-compatible wrappers that delegate to the resolved `BoltzSwapProvider`. Adds `InspectSwapRecoveryAsync` (per-swap) and `ScanRecoverableSwapsAsync` (bulk) for read-only `SwapRecoveryInfo` diagnostics across all swap types — recovery itself still runs inside `BoltzSwapProvider.PollSwapState`. `DisposeAsync` now unsubscribes both `SwapsChanged` and `VtxosChanged` from storage. `ArkSwap.Route` + `ArkSwap.ProviderId` round-trip through the existing jsonb `Metadata` column under five constants (`ProviderId`, `RouteSource{Network,AssetId}`, `RouteDestination{Network,AssetId}`) — no schema migration; a dedicated column + migration is a follow-up. **PR #116** added the deterministic-preimage recovery scheme. `internal static byte[] BuildPreimageMessage(OutputDescriptor descriptor, uint index)` formats `PreimageTag || xonly_pubkey(32) || u32_le(index)` (anchored on `.Extract().XOnlyPubKey.ToBytes()` — canonical x-only, independent of the descriptor's string form so an HD signing descriptor and the bare receiver descriptor a restore reconstructs hash to the same message); `private async Task<byte[]> DerivePreimageAsync(walletId, descriptor, index, ct)` resolves the wallet's signer, BIP-340-signs the SHA-256 message hash (`aux_rand=null` for determinism), and returns `SHA256(sig.ToBytes())`. `InitiateReverseSwap` / `InitiateBtcToArkChainSwap` / `InitiateArkToBtcChainSwap` call `DerivePreimageAsync(walletId, descriptor, index: 0, ct)` and pass the bytes through the new optional `byte[]? preimage = null` parameter on `BoltzSwapsService.{CreateReverseSwap, CreateBtcToArkSwapAsync, CreateArkToBtcSwapAsync}` (null = legacy random behaviour). Watch-only wallets (signer `null`) fall back to `RandomUtils.GetBytes(32)`. `RestoreSwaps`'s reverse-swap branch re-derives a candidate preimage with `index=0` for each Boltz-rediscovered swap, hashes it, and on match against `restored.PreimageHash` attaches the hex to `SwapMetadata.Preimage` so the sweeper can claim the VHTLC; submarine swaps are excluded (Boltz controls that preimage). `PreimageTag = "Arkade-Boltz-Preimage-v1"` is intentionally protocol+provider scoped so any sibling Arkade SDK reproduces the same preimage from the same wallet material — versioned for future scheme bumps. Cross-SDK byte layout pinned by `NArk.Tests/PreimageDerivationTests.cs`. **PR #138** made the reverse-swap fee payer configurable: `InitiateReverseSwap` gains an optional `ReverseSwapFeePayer feePayer` overload (default `Recipient`), threaded through to `BoltzSwapService.CreateReverseSwap`. `BuildReverseAmounts` maps the enum to the single Boltz amount field pinned — `Recipient` → `invoiceAmount = requested` (invoice equals the requested amount so LNURL-pay / LUD-06 wallets accept it; receiver nets `requested − fee`), `Sender` → `onchainAmount = requested` (receiver nets exactly requested; invoice inflated to `requested + fee`, not LUD-06-safe). Fixes the prior bug where `OnchainAmount` was always pinned, inflating the returned BOLT11 by the swap fee so lightning-address payments stuck at `swap.created → invoice.expired`. `ValidateReverseAmounts` checks Boltz's response against the fee-payer contract and `ResolveExpectedOnchainAmount` computes the on-chain amount stored as `ArkSwap.ExpectedAmount` (previously the raw requested amount). `ReverseResponse` gains a nullable `OnchainAmount`; `BoltzSwapService` now also runs the reverse fees through `BoltzLimitsValidator.ValidateFeesAsync`. Both modes covered by `NArk.Tests/Swaps/ReverseSwapAmountTests.cs` + `NArk.Tests.End2End/Swaps/ReverseSwapAmountTests.cs`.
- `Boltz/BoltzSwapProvider` -- Boltz-specific `ISwapProvider`. All Boltz protocol logic (status polling, persistent websocket monitoring, cooperative refunds, MuSig2 claiming, cross-signing, 10-consecutive-404 unknown-to-provider safety net, per-wallet `BeginScope(("WalletId", id))` at all entry points) lives here. New: chain-swap renegotiation on `transaction.lockupFailed` (`TryRenegotiateChainSwap` calls `GET → POST /v2/swap/chain/{id}/quote`, guarded by `BoltzLimitsValidator` + a status-probe race-tolerant disambiguation); cooperative BTC-side refund (`CoopRefundBtcToArkChainSwap`) and ARK-side refund (`CoopRefundArkToBtcChainSwap`) for chain swaps in both directions; `swap.expired` + no-funds-locked → `Failed` guard; `SwapStatusChanged` raised on every persisted status transition (subscriber exceptions caught + logged); `StartAsync`'s linked CTS stored in `_linkedStartCts` and disposed in `ShutdownAsync`; `StopAsync` is no longer a no-op (`ShutdownAsync` factored out, guarded by an `Interlocked` sentinel); `_swapsIdToWatch` is now `ConcurrentDictionary<string, byte>` instead of a reassigned `HashSet<string>`; single long-lived Boltz websocket (`_websocket` guarded by `_websocketLock`, `RunWebsocketLoop`, 5 s reconnect backoff, re-subscribes from `_swapsIdToWatch`). **PR #141** added unilateral refund fallbacks for when Boltz permanently refuses the cooperative co-sign: `UnilateralRefundBtcToArkChainSwap` spends the BTC HTLC via its refund tapscript leaf once `lockupDetails.TimeoutBlockHeight` (CLTV) is reached (`BtcHtlcScripts.GetRefundLeaf` + `BtcTransactionBuilder.SignScriptPathRefund`, Boltz supplies the timeout as a plain int — no script parsing); the provider subscribes to `IIntentStorage.IntentChanged` (`OnRefundIntentChanged`, wired in `.Lifecycle.cs`) to poll immediately on batch settlement. `TryCoopRefundBtcToArk` renamed `TryRefundBtcToArk` (now covers coop + unilateral); renegotiation acceptance re-polls immediately; cooperative-refund/claim fees moved from the flat 250-sat `DefaultRefundClaimFeeSats` to mempool-driven `EstimateClaimRefundFeeAsync` (`IBitcoinBlockchain.EstimateFeeRateAsync(confirmTarget: 2)` × ~111 vBytes). **PR #123** split the class into four partials (`.cs` / `.Lifecycle.cs` / `.Claims.cs` / `.Refunds.cs`) so each topic (state + ws, lifecycle, claim flows, refund flows) reads as its own file; the routing surface delegates to a new `BoltzRouteHelper` (`SupportsRoute` / `GetAvailableRoutesAsync` / `GetLimitsAsync` / `GetQuoteAsync`); `PollSwapState` now switches over a `BoltzSwapAction?` returned by `BoltzOperationClassifier.Classify(swap, boltzStatus)` (replacing nested-if recovery dispatch with a flat switch); `BoltzSwapStatus` lifts every Boltz lifecycle status string into a `const` (`SwapCreated`, `SwapExpired`, `TransactionMempool`, `TransactionConfirmed`, `TransactionServerMempool`, `TransactionServerConfirmed`, `TransactionLockupFailed`, `TransactionFailed`, `TransactionClaimPending`, `TransactionClaimed`, `TransactionRefunded`, `InvoiceSet` / `InvoicePending` / `InvoicePaid` / `InvoiceFailedToPay`, `InvoiceSettled` / `InvoiceExpired`, `MinerFeePaid`) + `ToArkSwapStatus(string)` that maps only the genuinely-terminal statuses to `ArkSwapStatus` and returns `null` for operational ones, forcing classifier routing. ## Wallet Signing (capability via composition, not enum cases)

The wallet model has two **orthogonal** axes — keep them separate at every layer:

1. **Key-derivation flavour** — `WalletType { SingleKey, HD }`. Decides the descriptor shape (`tr(pubkey)` vs `tr([fp/path]xpub/0/*)`) and is *all* `WalletType` encodes (PR #107 reverted an earlier attempt to add `WatchOnly` / `Remote` enum cases because they conflated key-derivation with key-availability — the smell showed up where the address provider had to recover the derivation by sniffing the descriptor string).
2. **Signing capability** — answered at `IWalletProvider.GetSignerAsync` time, *not* by a tag on the data. `ArkWalletInfo.Secret` is nullable; `null`/empty means "no local key" — watch-only or remote-signed.

`DefaultWalletProvider.GetSignerAsync(walletId)` resolves the capability:

| `ArkWalletInfo.Secret` | `IRemoteSignerTransport.KnowsWalletAsync` | Returns |
| --- | --- | --- |
| non-empty | — | `CompositeArkadeWalletSigner` with the matching local `IDescriptorSigningSource` (`Bip39SigningSource` for HD, `NsecSigningSource` for SingleKey) |
| null / empty | `true` | composite with `RemoteTransportSigningSource` only |
| null / empty | `false` (or no transport registered) | `null` (watch-only) |

The sole `IArkadeWalletSigner` impl is `CompositeArkadeWalletSigner` — a fan-out over one or more `IDescriptorSigningSource`s. Each source answers `CanProvideAsync(descriptor)` and exposes the operation-level signing methods (`Sign`, `SignMusig`, `GenerateNonces`, `GetPubKey`); the composite dispatches each call to the first source that claims the descriptor. Order is significant: `DefaultWalletProvider` registers local sources first, remote as fallback. Custom sources (HWI, threshold key share, in-browser session signer) implement `IDescriptorSigningSource` and either compose with `DefaultWalletProvider` (when a follow-up enriches the wiring) or replace `DefaultWalletProvider` outright.

Note on the boundary: `IDescriptorSigningSource` is *operation-level* (Sign/SignMusig/GenerateNonces) — it never returns `ECPrivKey`. That's load-bearing for the remote case: a remote source can implement the contract honestly without round-tripping secret material over the wire. The original sketch in #112 returned `ECPrivKey` and would have defeated remote signing.

Migration note: the three concrete `IArkadeWalletSigner` implementations (`HierarchicalDeterministicWalletSigner`, `NSecWalletSigner`, `RemoteArkadeWalletSigner`) were **deleted** in PR #114. Direct constructors are gone; consumers that used them are equivalent to a `CompositeArkadeWalletSigner` over the matching single source. `NsecSigningSource.FromNsec` mirrors the old `NSecWalletSigner.FromNsec` static for the most common entry-point migration.

## MuSig2 Nonce Lifecycle (secret nonce stays inside the signer)

Before PR #113, `IArkadeWalletSigner.GenerateNonces` returned `MusigPrivNonce` (the secret half) and `SignMusig` required the caller to pass it back. That made the secret nonce cross the signer boundary — for the remote-signer transport that meant the "remote signer" *wasn't* actually one (secret material round-tripped over the wire), and for in-process signers it encouraged callers to hold MuSig2 secrets in their own data structures (where accidental reuse leaks the private key — MuSig2 nonce reuse is catastrophic).

Reshaped contract (PR #113), preserved on the local signer + transport surfaces:

- `GenerateNonces(descriptor, context, sessionId)` returns `MusigPubNonce` only. The signing source derives the secret nonce internally and stores it in a per-instance `ConcurrentDictionary<string, MusigPrivNonce>` keyed by `sessionId`.
- `SignMusig(descriptor, context, sessionId)` drops the `MusigPrivNonce` parameter. The signing source looks the secret up by `sessionId` and consumes it on use (`TryRemove`) so the store is self-evicting on the happy path.
- `GenerateNonces` throws if a nonce is already stored for the same `sessionId` (calling twice without an intervening `SignMusig` would orphan secret material — almost certainly a caller bug).

Why `sessionId` and not `MusigContext.AggregatePubKey`: in a batch tree, multiple transactions can share the cosigner set + taproot tweak, so their `MusigContext`s produce identical `AggregatePubKey` but different sighashes. The sighash is internal to `MusigContext` and not externally observable, so the signer can't disambiguate on its own. The caller — `TreeSignerSession` — is the only one with enough information; it passes the tree-node txid as `sessionId`. `TreeSignerSession._myNonces` collapsed to `Dictionary<uint256, MusigPubNonce>` — the secret half no longer round-trips through the batch coordinator.

`IRemoteSignerTransport` documents that long-lived transports need an eviction policy (TTL or bounded count) for abandoned nonces. In-process signers get away with remove-on-consume because their lifetime is the batch session; a server-side transport could leak unconsumed entries if a client generates a nonce and never signs.

**`IRemoteSignerTransport.SignAsync` `aux_rand=null` SHOULD requirement (PR #116)** — `<remarks>` on `SignAsync` now requires implementations to sign with `aux_rand` set to null (or all-zero) so the signature is deterministic per `(key, hash)`. `SwapsManagementService.DerivePreimageAsync` depends on this for the swap-preimage recovery scheme: same descriptor + same wallet must produce the same signature, otherwise a restored wallet that rediscovers an outstanding reverse/chain swap via Boltz's `/v2/swap/restore` re-derives a different preimage and fails to claim the VHTLC. Transports that randomise `aux_rand` (e.g. hardware-signer side-channel hardening) still execute swaps fine; only the post-restore claim story is lost for remote-signed wallets. Local sources (`Bip39SigningSource`, `NsecSigningSource`) already pass `aux_rand=null` so they satisfy the contract by construction.

Signer caching (PR #113 + simplified in PR #114): `DefaultWalletProvider` caches signers per `wallet.Id` so the in-process nonce store survives between the `GenerateNonces` call and the matching `SignMusig` call. A fresh signer per call would silently break MuSig2 signing — the second call would always find an empty store and throw. PR #114 collapsed the original `(walletId + secret hash + transport)` cache key to `wallet.Id` alone (re-import is an out-of-band event handled by host restart) and moved the cache hit short-circuit above source construction so the hot batch-participation path skips per-VTXO master-fingerprint derivation + `KnowsWalletAsync` round-trips entirely.

## VTXO Sync (subscription + safety-net poll)

`VtxoSynchronizationService` keeps **one long-lived arkd `GetSubscription` stream** open through a supervisor loop (`RunStreamSupervisorAsync`) and mutates the watched script set **in place** (PR #103, retargeted to arkd's unified subscription API in PR #148). The supervisor opens the stream via `OpenSubscriptionStreamAsync(initialScripts, existingSubscriptionId)` and stores the id carried by the first `VtxoSubscriptionStarted` event in `_subscriptionId`; pushes arrive as `VtxoScriptsChanged`. When `UpdateScriptsView` sees a delta it issues a single `UpdateSubscriptionScriptsAsync(_subscriptionId, added, removed)` rather than tearing the stream down. The supervisor reconnects on the same id; if arkd reports the subscription not found (TTL-GC'd after a longer disconnect, surfaced as a `NotFound` error), the service clears `_subscriptionId`, signals the supervisor via `SignalStreamGenerationChange`, and the next loop reopens fresh (null id, current set passed as initial filter) with a full-history catch-up poll for the recreated set. An empty active set disconnects the stream and the supervisor goes idle on `_streamWakeup` until scripts return. `StreamReconnectDelay = 1s` between transient stream faults. The 5-second safety-net `RoutinePoll` re-derives the active script set **fresh** from `IActiveScriptsProvider`s every tick via `GatherActiveScriptsAsync` (PR #102) and reconciles the subscription to that set — a stale or missed `ActiveScriptsChanged` event can never hide a script from detection. A failing provider is logged and skipped (per-provider isolation). `EfCoreVtxoStorage.GetActiveScripts` overrides the default with a `DISTINCT script` projection, so the per-tick derive stays cheap even for wallets with thousands of unspent VTXOs. `_lastViewOfScripts` was renamed `_subscribedScripts` and demoted to pure stream-subscription bookkeeping (it tells the supervisor when to recompare; it is no longer the source of truth for what to poll).

## VTXO Sync Cursor (per-wallet metadata)

The service also persists a cold-start catch-up cursor through the generic wallet metadata API instead of a dedicated table:

- Constant `VtxoSynchronizationService.LastFullPollAtMetadataKey = "vtxo.lastFullPollAt"`.
- Cold-start: reads `MIN(per-wallet vtxo.lastFullPollAt)` across `IWalletStorage.LoadAllWallets()` and uses it as the `after` filter on the first `UpdateScriptsView`. If any wallet has no cursor (or an unparseable value), the MIN bails to `null` so a fresh wallet's first-time scripts aren't skipped via someone else's cursor.
- Routine-poll success (`PollRequest.IsFullSetSnapshot=true`): writes the poll's `StartedAt` to every wallet's `vtxo.lastFullPollAt`. Stream-driven and newly-added-script polls do NOT advance the cursor — they cover only a subset.
- A `_coldStartCatchupComplete` gate (volatile bool) blocks all cursor writes until the first cold-start catch-up succeeds, so a failed catch-up followed by a successful routine poll cannot advance the cursor past the gap. The cold-start catch-up itself is marked `IsFullSetSnapshot=true`, so success advances the cursor immediately.
- The service takes `IWalletStorage` as an *optional* constructor parameter — when absent, the gate defaults to `true` and the service falls back to `null`-after on cold start (current behaviour, opt-out preserved).

This design replaces an earlier dedicated `ISyncStateStorage` / `ArkSyncStateEntity` in PR #78. Storage footprint now: one JSON column on an existing entity, written via `IWalletStorage.SetMetadataValue` — no new table, interface, or downstream migration.

## Chain-Time Cache & Fallback

`RPCChainTimeProvider.GetChainTime` caches `(Timestamp, Height)` on every successful Bitcoin Core RPC call. If a subsequent call fails (transient 5xx during reindex / IBD / heavy load) AND a cached value exists, it returns the cache and logs a warning. Cold-start failures (no cache yet) still throw. Prevents a single transient `getblockchaininfo` 500 from forcing controller-bound consumers (e.g. BTCPay's plugin manager) to disable the plugin. `ChainTimeProvider` (NBXplorer wrapper) accepts an optional `ILogger<RPCChainTimeProvider>` so consumers can surface the fallback warning; default-null keeps the change non-breaking.

## Per-Wallet Log Scopes

Per-wallet entry points in `SwapsManagementService` (Initiate*, Pay*, Restore, `PollSwapState` iteration body), `BatchManagementService` (`RouteToBatchSessionsAsync`, `HandleBatchStartedForAllIntentsAsync` per-intent loops), `OnchainService.InitiateCollaborativeExit` (both overloads), `IntentGenerationService` (`GenerateManualIntent` + periodic per-wallet loop), `SpendingService` (`Spend` overloads + `GetAvailableCoins`), `AssetManager.{Issue,Reissue,Burn}Async`, `HdWalletRecoveryService.ScanAsync`, `DelegationMonitorService.ProcessVtxoAsync`, and `SweeperService.Sweep` (per-coin loop) all open `using (logger.BeginScope(("WalletId", id)))` so downstream sinks can route every transitively-emitted log line to the right wallet — including ones whose templates don't already carry `{WalletId}`. `VtxoSynchronizationService` is intentionally *not* scoped: its streams/polls span all active wallets at once.

## Multi-Provider Swap Architecture

Replaces the previous monolithic `SwapsManagementService`-owns-Boltz design (PR #79):

- `ISwapProvider` is the contract every provider implements. Methods declared on the interface that are inherently provider-specific (`CreateSwapAsync`, `RefundSwapAsync`) were removed during the refactor — providers expose creation through their own typed APIs and refund logic lives inside the provider's poll loop. Notification hooks (`NotifyVtxoChanged`, `NotifySwapChanged`) ship default no-ops so the router doesn't have to type-check.
- `SwapsManagementService` is now the router. It owns `IEnumerable<ISwapProvider>`, subscribes once to storage events, and dispatches notifications to every provider via the default-no-op hooks. Public methods (Initiate* / PayExisting* / Restore*) resolve the registered `BoltzSwapProvider` and delegate, preserving the existing API surface for consumers.
- Per-swap routing metadata (`ArkSwap.Route`, `ArkSwap.ProviderId`) round-trips through the existing jsonb `Metadata` column via five constants (`ProviderId`, `RouteSource{Network,AssetId}`, `RouteDestination{Network,AssetId}`). Legacy rows yield `(null, null)` on read so the default-provider fallback kicks in. A follow-up that adds dedicated columns + a migration can drop these constants.
- `BoltzSwapProvider` carries all Boltz state — websocket, _swapsIdToWatch (`ConcurrentDictionary<string, byte>`), per-swap consecutive-404 counter, persistent websocket lifecycle, MuSig2 session caches — and observes wallet-context via `BeginScope(("WalletId", id))` at all per-wallet entry points. `StartAsync`'s linked CTS is stored on `_linkedStartCts` and disposed in `ShutdownAsync` to avoid leaking the `CancellationTokenRegistration`. `StopAsync` is no longer a no-op (`ShutdownAsync` factored out, guarded by an `Interlocked` sentinel so `StopAsync` + `DisposeAsync` compose without double-await).
- Chain-swap unhappy-path recovery is implemented inside `BoltzSwapProvider.PollSwapState`:
  - **Renegotiation** on `transaction.lockupFailed` via `TryRenegotiateChainSwap` (`GET → POST /v2/swap/chain/{id}/quote`). Guarded by `BoltzLimitsValidator` (rejects amounts ≤ 0 or outside Boltz's chain-swap limits). Race-tolerant: on POST 4xx the provider probes Boltz's current status — if it has moved past `transaction.lockupFailed` (concurrent tick already accepted) the renegotiation is treated as successful.
  - **Cooperative BTC refund** (`CoopRefundBtcToArkChainSwap`): for refundable BTC→ARK chain swaps, build the refund tx via `BtcTransactionBuilder.BuildKeyPathClaimTx`, sign via `ChainSwapMusigSession.CooperativeRefundAsync`, broadcast via Boltz, mark `Refunded`.
  - **Cooperative ARK refund** (`CoopRefundArkToBtcChainSwap`): for refundable ARK→BTC chain swaps, snapshot-poll arkd for VHTLC VTXOs, derive a fresh refund destination via `SwapExtensions.GetOrDeriveRefundDestinationAsync` (persisted as `SwapMetadata.RefundDestination` on first attempt and reused on retries so each tick doesn't leak an orphan contract row), build the Ark refund tx, ask Boltz to co-sign via `RefundChainSwapArkAsync`, merge Boltz's signed PSBTs, submit via `SubmitArkTransaction`, mark `Refunded`. Picks the canonical VTXO (`vtxos.FirstOrDefault(v => v.Amount == swap.ExpectedAmount)`) on double-funded scripts — extras are left to `SweeperService`. **PR #123** moved the refund-destination caching into a reusable `SwapExtensions.GetOrDeriveRefundDestinationAsync` extension (also used by submarine refund per the same PR — "feat(swaps): refund destination for boltz submarine swaps").
  - **`swap.expired` with no funds locked** → `Failed` with explanation (otherwise the refund branch keeps retrying forever for swaps that have nothing to recover).
  - **Unilateral refund fallbacks** (PR #141), reached when Boltz permanently refuses the cooperative co-sign: BTC→ARK chain swaps fall through `TryRefundBtcToArk` to `UnilateralRefundBtcToArkChainSwap` (script-path CLTV spend of the BTC HTLC once `lockupDetails.TimeoutBlockHeight` is reached); submarine and ARK→BTC swaps fall through to `TryRefundWithoutReceiverAsync`, which submits the VHTLC `refundWithoutReceiver` spend as an Arkade batch intent (via optional `IIntentGenerationService`) once `VHTLCContract.RefundLocktime` elapses. `CheckRefundWithoutReceiverIntentAsync` (consulted *before* each coop attempt and before re-submitting) reads `SwapMetadata.RefundIntentTxId`: intent settled → mark `Refunded`; in-flight → wait (don't re-attempt or mark `Failed`); terminal-failure/absent → (re-)submit. This matters because once the refund batch settles the lockup VTXO is spent, so a naive subsequent poll would see "no lockup" and wrongly mark the swap `Failed`. The `refundWithoutReceiver` closure now also handles block-height (not just time-lock) CLTVs — `VHTLCContractTransformer` compares `chainTime.Height >= RefundLocktime.Value` for height locktimes (previously only the `IsTimeLock` branch was handled, so a block-height refund locktime never triggered).

## Pending Arkade Transaction Recovery

`PendingArkTransactionRecoveryService` (in `NArk.Core/Services/`) reconciles off-chain txs stranded between `SubmitTx` (server locked the inputs as in-flight) and `FinalizeTx` (crashed before sending the final checkpoint signatures). Without this recovery the server holds the inputs hostage and the user's coins are stuck.

- Runs on host startup via `ArkHostedLifecycle` (after `VtxoSync` so the local VTXO state reflects the in-flight projection).
- Sweeps every wallet known to `IWalletStorage`. For each wallet:
  1. Loads VTXOs from local storage with `includeSpent: true` — the in-flight projection marks the input VTXO as `IsSpent=true`, but BIP-322 only signs an identity message so spent VTXOs are valid proof material.
  2. Batches inputs by 20 (`MaxInputsPerProof` — matches the go-sdk and ts-sdk batching shape and the server's hard cap).
  3. Builds a BIP-322 ownership proof anchored on each batch's first VTXO (`SignBip322Proof` now returns the signed PSBT so callers see the leaf script — a latent bug that arkd's strict `GetPendingTx` path uncovered).
  4. Calls `IClientTransport.GetPendingTxAsync(proof, batch)` — the new transport endpoint.
  5. For every pending tx the server returns, signs the checkpoint PSBTs with the wallet's signer and calls `IClientTransport.FinalizeTx`.
- Per-tx failures raise `RecoveryFailed` (`PendingTxRecoveryFailureEventArgs`) and are skipped — one bad tx never blocks the wallet from booting. The next host start retries any unfinalized leftovers. Subscriber exceptions are caught and logged but never propagate.
- `RecoverAllWalletsAsync` catches general exceptions (not just `OperationCanceledException`) so DB timeouts / connection errors / corrupted state can't kill host startup — the sweep is genuinely best-effort.
- `FinalizePendingArkTransactionsAsync(walletId)` is the on-demand surface (e.g. immediately after a user unlock). **Timing note**: arkd's in-flight projection is async, so the same-process E2E reproducer can race the projection within ~1 s of `SubmitTx`. Production never hits this — recovery runs at host startup, well after any crash. Callers invoking recovery in the same process that just crashed should retry briefly.

## Unilateral Exit Pipeline

`UnilateralExitService` (in `NArk.Core/Services/`) drives the full exit flow when arkd is unavailable or uncooperative. State machine: `Broadcasting` → `AwaitingCsvDelay` → `Claimable` → `Claiming` → `Completed` (or `Failed` with `FailReason` if a step exceeds `MaxBroadcastRetries=10`).

**Two operating shapes**:

- **Stateful (`StartExitAsync` + `ProgressExitsAsync`)** — idempotent re-invocation for the same outpoint (returns the existing session, no duplicates). Watchtower can observe sessions via `GetActiveSessionsAsync` / `GetByVtxoAsync`. Requires either `ConfigureArkExitEntities()` (EF Core, persistent) or `AddInMemoryExitStorage()` (`ConcurrentDictionary`, lost on restart).
- **Stateless (`BroadcastExitChainAsync` + `ClaimMaturedExitAsync`)** — pure pass-through with zero exit-specific persistence. `BroadcastExitChainAsync(walletId, vtxoOutpoint, claimAddress)` fetches the chain fresh from arkd, broadcasts every off-chain row that isn't already on-chain, and returns an `ExitPlan` record (wallet id, vtxo outpoint, claim address, leaf txid, CSV delay). Caller persists `ExitPlan` in whatever form they want (JSON blob, settings entry, file on disk), and feeds it back to `ClaimMaturedExitAsync` once they think the CSV timelock has matured. Returns the claim txid on success, `null` when CSV hasn't matured (caller polls again later), or throws when the leaf-tx hasn't even confirmed yet. Trade-off vs. stateful path: no idempotency (re-broadcasts if called twice), no automatic watchtower progression — gain is zero exit-specific schema or DI footprint.

**Backing services**:

- `VirtualTxService` — Fetches and stores virtual-tx branches via `IClientTransport.GetVtxoChainAsync` + `GetVirtualTxsAsync`. `VirtualTxOptions.DefaultMode` defaults to `Lite` (txids + expiry only — most VTXOs settle into the next batch or get spent off-chain, so the hex fetch is deferred to `StartExitAsync`'s `EnsureHexPopulatedAsync`). `Full` mode stores raw tx hex at every VTXO arrival (two arkd round-trips per VTXO, scaling with chain depth) — opt in for strict offline-exit requirements. Stores the **whole chain** including the on-chain `Commitment` root tagged with `ChainedTxType` (`Unspecified` / `Commitment` / `Ark` / `Tree` / `Checkpoint`); `Commitment` rows have null hex since arkd's `GetVirtualTxs` doesn't carry on-chain hex (the tx is already on-chain). `EnsureHexPopulatedAsync` ignores `Commitment` when deciding whether a branch is fully populated; `ProgressBroadcastingAsync` skips `Commitment` rows in its broadcast loop. Per-tx model deduplicates shared tree nodes across sibling VTXOs.
- `ParseVirtualTx` — Branches on `ChainedTxType`: **Tree** txs lift `PSBT_IN_TAP_KEY_SIG` (NBitcoin's `psbtInput.TaprootKeySignature`) and assemble `WitScript(new[] { sig.ToBytes() }, true)` directly — tree txs are MuSig2-cosigned via the taproot key-path and arkd's PSBT omits `witness_utxo` / `non_witness_utxo` (which `PSBT.Finalize` would require). **Ark / Checkpoint / Unspecified** try `Finalize+ExtractTransaction`, falling back to lifting `FinalScriptWitness` on `PSBTException`. **Commitment** is filtered out one layer up (already on-chain).
- `P2ACpfpBuilder` — Builds v3 CPFP children for 1p1c package relay so the v3 (TRUC) tree txs can ride out Bitcoin Core's TRUC-violation check (the parent has only a 0-sat P2A anchor). Two-stage fee-rate adjustment (signs twice if vsize estimate was off). Takes an `IFeeWallet` for the sighash-callback signing path — the SDK computes the sighash and asks the wallet for a `SecpSchnorrSignature` via `SignFeeUtxoAsync(outpoint, sighash, sighashType)`, so the wallet can produce it however it likes (in-memory `Key`, hardware device, HSM, remote signer, BTCPay's internal signer). `IFeeWallet.SelectFeeUtxoAsync` returns `ICoin?` (NBitcoin standard; no parallel `FeeUtxo` type). `UnilateralExitService.BroadcastWithCpfpAsync` activates the CPFP path when an `IFeeWallet` is registered; gracefully falls back to direct broadcast when not (regtest `minrelaytxfee=0` makes that acceptable for tree txs, downstream consumers wanting CPFP supply the fee wallet).
- `ExitWatchtowerService` + `ExitWatchtowerBackgroundService` — Detect partial tree broadcasts (someone else started unrolling a tree branch) and auto-start exits on owned VTXOs whose ancestors hit the chain. Derives a boarding-contract claim address via `IContractService`. Skips VTXOs without stored branches before making RPC calls.
- `VtxoChainAutoFetchService` — Opt-in (`AddVirtualTxAutoFetch()`) hosted service that listens to `IVtxoStorage.VtxosChanged` and queues a chain fetch for every new VTXO above the configured worth-threshold. Replaces the batch-only `PostBatchVirtualTxFetchHandler` — VTXOs arrive from many sources (batch, change from a spend, incoming payment, swap claim, sweep), all of which can later need a unilateral exit. `FetchAndStoreBranchAsync`'s `HasBranchAsync` short-circuit makes duplicate events cheap. `PostSpendVirtualTxPruneHandler` stays auto-wired (cleanup is safe regardless of whether auto-fetch is on).

**Storage shape**:

- `IExitSessionStorage` — Tracks per-exit sessions with `RetryCount`, `FailReason`, state filters (`GetActiveSessionsAsync` skips `Failed`/`Completed`; `GetByVtxoAsync` returns sessions in any state so callers can see why a Failed session went bad).
- `IVirtualTxStorage` — Per-tx model with shared-node deduplication across sibling VTXOs; orphan cleanup on prune respects shared chain nodes (won't drop a tx still referenced by another live VTXO).

## Network Configurations

Pre-configured networks via `ArkNetworkConfig`:
- **Mainnet**: `arkade.computer` / `arkade.money` / `api.boltz.exchange` (the `ark.` subdomain was dropped in PR #82; mutinynet and regtest endpoints unchanged)
