# Ark TypeScript SDK — Project Overview

## What is ts-sdk?

The Ark TypeScript SDK (`@arkade-os/sdk`) is the official client library for building Bitcoin wallets with Ark protocol support. It enables applications to create, manage, and transact with virtual UTXOs (VTXOs) — off-chain Bitcoin outputs that settle on-chain through Ark's batched round mechanism.

The SDK is designed to run across all JavaScript environments: browsers, Node.js, React Native/Expo, and service workers.

## Monorepo Layout

Since 2026-05-22 the `arkade-os/ts-sdk` repository is a **pnpm workspace monorepo** (`pnpm-workspace.yaml`) that ships two published packages:

| Workspace path | Published as | Version (at HEAD) | Role |
|----------------|--------------|-------------------|------|
| `packages/ts-sdk/` | `@arkade-os/sdk` | `0.4.45` | This SDK — what the rest of this doc describes |
| `packages/boltz-swap/` | `@arkade-os/boltz-swap` | `0.3.50` | Sibling Boltz Lightning/chain-swap library; depends on `@arkade-os/sdk` via `workspace:*` (see `docs/projects/boltz-swap/`) |

- **devDeps hoisted to root**: `tsup`, `vitest`, `typescript`, `prettier`, `husky`, `@types/node`, `fake-indexeddb`, `eventsource`. Per-package `package.json` keeps only package-unique deps.
- **Shared base configs**: root `tsconfig.base.json`, root prettier config, root `tsup` base extended per-package.
- **Single regtest driver**: `scripts/regtest.sh <ts-sdk|boltz-swap> <up|setup|test|down|reset|cycle>` from the repo root. Each package supplies its own `.env.regtest`.
- **Package-scoped releases**: `pnpm run release -- sdk patch` (SDK + dependent boltz-swap patch), `pnpm run release -- boltz-swap patch` (Boltz-only bugfix), `pnpm run release -- sdk prepatch --preid beta` (mirrors prerelease into boltz-swap), `pnpm run release -- all patch` (bump both). Driver: `scripts/release.sh` → `scripts/release.mjs`; gated on `pnpm test:unit` (monorepo-wide) before publish.
- **Single `bip68` ambient declaration** hoisted to the monorepo root (was duplicated per-package).
- **No published API impact**: the npm-published `@arkade-os/sdk` tarball path is unchanged; downstream consumers installing from npm are unaffected by the workspace shape.

| BatchSignableIdentity One-Popup Path | When the wallet's `Identity` implements `BatchSignableIdentity` AND every signable input across the arkTx + N checkpoints resolves to the baseline key (per `InputSignerRouter.canBatch`), `Wallet.buildAndSubmitOffchainTx` and the pending-tx recovery loop in `finalizePendingTxs` collapse the N+1 wallet popups into a single `identity.signMultiple(requests)` call. This restores the optimization originally shipped in #395 that was silently lost when per-input routing moved into `InputSignerRouter` (which signed one PSBT at a time, making `signMultiple` unreachable). **Send path**: user-signed arkTx + checkpoints are kept; the unsigned checkpoints are submitted to arkd for its tapScriptSig; server + user sigs are merged via `combineTapscriptSigs` (input-count + per-input `tapScriptSig` invariants now explicit — rejects mismatches with input-indexed errors instead of silently appending `undefined`). A symmetric length guard rejects a server response carrying a wrong checkpoint count. **Recovery path**: `finalizePendingTxs` hands `signMultiple` checkpoints already carrying the server's `tapScriptSig` and consumes the returned transactions directly — the `BatchSignableIdentity` interface contract now explicitly requires implementations to preserve any pre-existing partial signatures and only add their own, so no merge is needed. Mixed sends (arkTx non-batchable or a checkpoint missing a descriptor) fail fast at the unified `canBatch` call before any pending-tx state is recorded. Requests are deep-cloned (`tx.clone()`) before handing them to `signMultiple` so a misbehaving provider cannot mutate the originals before `submitTx`. | VTXO Operations | Get balance, send, receive, settle, renew, recover VTXOs. | Boarding Contract Handler | **Post-0.4.32**: `boarding` is a first-class registered contract type with its own handler (`src/contracts/handlers/boarding.ts`, `BoardingContractHandler` + `BoardingContractParams = DefaultContractParams` exported from the package root). The handler delegates `createScript` / `serializeParams` / `deserializeParams` / `selectPath` / `getAllSpendingPaths` / `getSpendablePaths` to `DefaultContractHandler` — boarding semantics come from the contract type and from sourcing `csvTimelock` from the server's `ArkInfo.boardingExitDelay` (the offchain `default` contract uses `ArkInfo.unilateralExitDelay`), not from renamed params. When the delays coincide (misconfigured/malicious server) the boarding script is byte-identical to the default script and the wallet must stay usable. The coalescence is now resolved by `ContractManager.createContract` FIRST-WINS — keeps the existing row exactly as-is (no overwrite, no type promotion, no throw); `areCoalescibleContractTypes(a, b)` recognizes the `default ↔ boarding` pairing (every other cross-type pairing is rejected). The "default wins" outcome at the index-0 baseline is achieved *structurally* — `setupWalletConfig` persists the default matrix BEFORE the boarding baseline, so first-wins keeps it `default`; the wallet-layer `ensureWalletContract` collapsed to a one-line thin pass-through and the old `areSameScriptBaselineTypesCompatible` helper was removed (replaced by `areCoalescibleContractTypes` in the persistence layer). The first-wins rule covers init and the restore scan with a single source of truth, and preserves the watcher invariant (the winning row was registered with the watcher when first persisted; never mutated → no promote-then-forget-the-watcher gap). Consumers MUST NOT rely on `contract.type === "boarding"` to identify the boarding purpose — resolve via `wallet.getBoardingAddress()` / `wallet.boardingTapscript` and match by script. `ensureWalletContract` + `areCoalescibleContractTypes` are `@internal` exports for unit testing only. |

1. **Web Wallet** — Browser-based Bitcoin + Ark wallet with localStorage/IndexedDB
2. **Mobile Wallet** — React Native/Expo app with AsyncStorage and expo-crypto
3. **Background Wallet** — Service worker for persistent background operation
4. **Watch-Only** — Monitor balances without signing capability
5. **SDK Integration** — Embed Ark payments into existing applications
6. **Asset Issuance** — Create and manage custom assets on the Ark protocol

## Integration Points

- **arkd**: REST API + SSE for settlement events, transaction submission, and info queries. Every arkd request carries the `X-Build-Version` (server-build compatibility guard, `"0.9.9"`) and `X-SDK-VERSION` (`ts-sdk/<package-version>`) headers; the `ArkProvider.onServerInfoChanged` event stream + `DigestMismatchError` surface server-signer rotation so the client can re-derive and migrate deprecated-signer VTXOs (see the Server-Signer Rotation core feature)
- **Indexer**: REST + streaming for address subscriptions, VTXO updates, transaction history
- **Esplora**: On-chain block explorer for UTXO lookups and transaction broadcasting (default `ESPLORA_URL` map points at Ark Labs–operated mempool deployments for bitcoin/signet/mutinynet; the `regtest` entry is now `http://localhost:3000/api` — note the `/api` suffix added on 2026-06-01 in `7e34960a` when the SDK migrated to the mempool-backed Esplora exposed by the in-house arkade-regtest stack, replacing the prior nigiri/chopsticks `http://localhost:3000`). **Regtest robustness fixes that landed together with the migration**: `EsploraProvider.getChainTip()` uses the standard `/blocks` route (newest-first array of recent blocks) rather than the non-standard `/blocks/tip` (`abd86ec3`) — `/blocks/tip` was an electrs alias, mempool returned `[]` for it which surfaced as `No chain tip found` and cascaded into the unroll / settle / sweep / delegate / vhtlc e2e suites. `EsploraProvider.getFeeRate()` returns `undefined` on a 404 from `/fee-estimates` rather than throwing (`5f9a6845`) — mempool (spec-correct) returns 404 for that route on regtest (exposes fees via `/api/v1/fees/recommended` instead), and every caller already falls back to `MIN_FEE_RATE` on undefined; other (5xx) failures still surface. **0.4.40 (#587)**: `OnchainProvider.getTxOutspends` now returns `{ spent; txid? }[]` (spender txid optional — some deployments omit it) and `ExplorerTransaction` carries an optional `vin?: { txid; vout }[]` so the wallet can recover a boarding output's commitment tx from the address history when `/outspends` omits the spender (the electrum provider omits `vin`, so consumers tolerate its absence)
- **Electrum**: WebSocket Electrum (`ElectrumOnchainProvider`) as an alternative onchain provider; `ELECTRUM_WS_URL` defaults to Ark Labs Fulcrum 2.1 endpoints (which support `broadcast_package` for atomic 1P1C TRUC relay), with electrs-compatible fallbacks (no `verbose` transaction.get usage); `ELECTRUM_TCP_HOST` provided for Node-side TCP transports
- **Delegate**: REST API for VTXO delegation (renewal outsourcing), consumed via `RestDelegateProvider` (formerly `RestDelegatorProvider`, deprecated alias)
- **arkade-regtest** (submodule at `regtest/`): Local Bitcoin regtest environment for integration testing — Docker Compose stack (arkd — the ts-sdk `.env.regtest` pins `ARKD_IMAGE` / `ARKD_WALLET_IMAGE` to **v0.9.11** since `618f055a`, up from the prior `v0.9.9-rc.0`; nbxplorer 2.6.7, mempool-backed Esplora at `localhost:3000/api`, btcpay Bitcoin Core authenticated via `rpcuser=admin1` / `rpcpassword=123`, fulmine on 7000–7002) driven by the zero-dependency Node CLI `regtest/regtest.mjs` (`start` / `stop` / `clean` / `faucet` / `mine`). Replaced the prior `nigiri`/`chopsticks`/`esplora` stack on 2026-06-01 (`7e34960a`); `BITCOIN_LOW_FEE` and per-package `ARKD_IMAGE` overrides were removed (baked into the compose base / inherit the submodule's blessed default — `v0.9.6`). Electrum-ws bridge on port 50003 unchanged
