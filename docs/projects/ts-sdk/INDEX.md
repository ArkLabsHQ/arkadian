# Ark TypeScript SDK — Project Index

**ts-sdk** is the official TypeScript SDK (`@arkade-os/sdk`) for the Ark protocol. It provides a complete client library for building Bitcoin wallets with Taproot and Ark virtual UTXO (VTXO) support. The SDK runs in browsers, Node.js, React Native/Expo, and service workers with pluggable storage adapters.

Since 2026-05-22 the repository is a **pnpm workspace monorepo** that vendors two published packages:

| Workspace path | npm package | Version | Purpose |
|----------------|-------------|---------|---------|
| `packages/ts-sdk/` | `@arkade-os/sdk` | `0.4.40` | This SDK (wallet, providers, crypto, repositories) — npm-published path inside the tarball is unchanged |
| `packages/boltz-swap/` | `@arkade-os/boltz-swap` | `0.3.45` | Sibling Boltz Lightning/chain-swap library (docs under `docs/projects/boltz-swap/`) |

devDeps, prettier config, `tsup` base config, and the `scripts/regtest.sh` regtest driver are hoisted to the repo root. Releases are package-scoped via `pnpm run release -- {sdk|boltz-swap|all} <bump>`.

## Key Concepts

- **Mainnet Defaults**: `Wallet.create` / `ReadonlyWallet.create` / `ServiceWorkerWallet.create` default `arkServerUrl` to `DEFAULT_ARKADE_SERVER_URL` (`https://arkade.computer`); `OnchainWallet.create` defaults `networkName` to `DEFAULT_NETWORK_NAME` (`bitcoin`); `ArkAddress` and `contractFromArkContractWithAddress` default HRP to `DEFAULT_ARKADE_HRP` (`ark`). The `getArkadeServerUrl({ arkServerUrl })` helper resolves the URL with the same fallback. **Since 0.4.28** (after the d682eac batch): the constructor of every default provider also defaults its URL — `new RestArkProvider()` / `new RestIndexerProvider()` / `new ExpoArkProvider()` / `new ExpoIndexerProvider()` resolve to `DEFAULT_ARKADE_SERVER_URL`; `new EsploraProvider()` resolves to `ESPLORA_URL[DEFAULT_NETWORK_NAME]` (the Ark Labs mempool deployment for bitcoin). `VtxoScript.address(prefix?)` defaults `prefix` to `DEFAULT_NETWORK.hrp` and `VtxoScript.onchainAddress(network?)` defaults to `DEFAULT_NETWORK`. New constants `DEFAULT_ARKADE_SERVER_URL`, `DEFAULT_NETWORK`, `DEFAULT_NETWORK_NAME` live in `src/networks.ts` (moved out of `src/wallet/index.ts` for the cycle-free chain `script → networks → provider`)
- **Wallet Config URL Deprecation**: `BaseWalletConfig.arkServerUrl` / `indexerUrl` / `esploraUrl` and `ServiceWorkerWalletOptions.arkServerUrl` / `indexerUrl` / `esploraUrl` / `delegatorUrl` are all marked `@deprecated` (JSDoc only — runtime behaviour unchanged). Provider-based config is the recommended path: pass `arkProvider`, `indexerProvider`, `onchainProvider` instances directly. The deprecated string fields will be removed in a future major version. `Wallet.create` example JSDocs were rewritten to drop the URL-based form. Refs #466
- **Dust Change Guard / DustChangeError**: `Ramps.collaborativeExit` / partial-offboard now pre-checks the residual change VTXO against the wallet's dust threshold and throws a typed `DustChangeError` (`change: bigint`, `dustAmount: bigint`) before forwarding the intent to arkd — wallet UIs can catch it and offer to exit the full balance instead of surfacing the raw server-side dust rejection (closes #458). The dust lookup is centralized in `src/wallet/utils.ts` (`getDustAmount(wallet): bigint` reads `wallet.dustAmount` when present, falls back to `FALLBACK_WALLET_DUST_AMOUNT = 330n`); `ramps.ts` and `vtxo-manager.ts` share the helper. `DustChangeError` is re-exported from the package root (`src/index.ts`)
- **ServiceWorkerWallet.restore()**: New `ServiceWorkerWallet.restore({ gapLimit })` mirror of `Wallet.restore` that drives the gap scan inside the service worker (the `materialize()` callback `scanContracts` needs cannot cross postMessage, so the whole scan runs worker-side; only `gapLimit` and the success/error envelope cross the wire). The `RESTORE_WALLET` message uses the streaming `sendMessageWithEvents` path and is marked **long-running** in `isLongRunningRequest()` alongside `SETTLE` / `RECOVER_VTXOS` / `RENEW_VTXOS` so the bus deadline never races a multi-minute indexer scan (liveness still covered by PING). `AggregateError` is not structured-clone-portable across browsers, so the worker explicitly serializes it (`SerializedAggregateError` wire envelope: `{ name: 'AggregateError', message, errors: { name; message }[] }`) and the page reconstructs via `deserializeAggregateError` so callers can inspect `.errors` (helpers + `isSerializedAggregateError` guard live in `wallet-message-handler.ts`). Signing-only entrypoint — `ServiceWorkerReadonlyWallet` does not expose `restore`
- **Wallet**: Full signing wallet (`Wallet`) or watch-only (`ReadonlyWallet`)
- **Identity**: Key management abstraction — SingleKey, SeedIdentity (HD), MnemonicIdentity. Seed-backed and watch-only identities take a wildcard descriptor template (`tr(.../0/*)`) and expose it as `identity.descriptor`
- **Descriptor Provider**: Pure rotating allocator (`getNextSigningDescriptor`) — `StaticDescriptorProvider` for single-key, `HDDescriptorProvider` for HD receive rotation. HD-capable providers can opt into the wallet's receive lifecycle by implementing `ReceiveRotatorFactory` (`createReceiveRotator` extension); the core `DescriptorProvider` contract stays free of wallet concerns so HSM-backed and other minimal providers don't have to know about rotation
- **HD Receive Rotation** *(post-0.4.26, re-merged in #489 after #488 revert)*: `WalletReceiveRotator` (`src/wallet/walletReceiveRotator.ts`) owns the `DescriptorProvider`, the `vtxo_received` subscription, the rotation chain mutex, the boot pubkey lookup, and the contract registration on rotate. Boot path: look up the active default/delegate contract tagged `metadata.source === 'wallet-receive'` matching the current `serverPubKey`; if found, reuse its pubkey (no provider call); else allocate index 0 via `provider.getNextSigningDescriptor()`. Rotation path: on each `vtxo_received` for the currently-tagged display contract, allocate next descriptor → rebuild `offchainTapscript` → register new tagged contract (`type: 'default'` or `'delegate'` matching the wallet's tapscript shape) → mark the prior tagged display `inactive` (the watcher keeps watching it while `lastKnownVtxos.size > 0` so funds in flight at the old address aren't lost). Rotations are serialized by an internal `_hdRotationChain` mutex; consecutive `rotate()` failures gate future attempts behind exponential backoff (1s → 2s → … → 60s cap, resets on success). Baseline multi-timelock matrix (default + delegate × every `walletContractTimelocks` entry) stays anchored to `identity.xOnlyPublicKey()` (index 0) on every boot — never re-registered at the rotated pubkey
- **WalletMode**: `WalletConfig.walletMode: 'auto' | 'static' | 'hd' | DescriptorProvider`. `'static'` skips HD wiring; `'hd'` requires an HD-capable identity with a rangeable descriptor (throws at `Wallet.create` otherwise — no silent fallback); passing a `DescriptorProvider` instance drives rotation through it (caller responsible for the identity matching). `'auto'` (default) is **explicitly short-term identical to `'static'`** until HD rotation has more soak time — flip-back criteria recorded under `TODO(hd-maturation)` in `resolveDescriptorProvider`. `ServiceWorkerWallet` only accepts the string forms (`ServiceWorkerWalletMode`) since the object form can't cross postMessage
- **Signing Router**: `InputSignerRouter` (`src/wallet/inputSignerRouter.ts`) dispatches per-input signing by looking up each input's owning contract. Rotated `default`/`delegate` contracts with a non-baseline owner are routed to `DescriptorProvider.signWithDescriptor` (using `metadata.signingDescriptor` persisted at rotation time); everything else (baseline owners, non-default/non-delegate contracts, the boarding script) goes to `Identity`. Inputs with no match are skipped silently. Throws `DescriptorSigningProviderMissingError` (no provider wired) or `MissingSigningDescriptorError` (a descriptor-capable `default`/`delegate`/`boarding` contract whose owner key is not this wallet's baseline and that carries no persisted `metadata.signingDescriptor`). **Since `89c8d411` (0.4.37)** the `MissingSigningDescriptorError` message enumerates both causes — the wallet was rotated on an earlier build that did not persist signing descriptors, *or* the contract belongs to a different identity (storage reuse) — and suggests setting `metadata.signingDescriptor`, restoring a pre-rotation snapshot, or deleting the contract. arkTx signing takes a per-input source-script override because checkpoint witnessUtxo scripts don't match the source VTXO's contract. **Since #535**: `classify(jobs)` extracted as the single source of truth for routing decisions (returns `InputRoutingPlan { identityIndexes; descriptorGroups }`); `sign()` consumes it. New variadic predicate `canBatch(...jobSets)` classifies the union of arkTx + N checkpoint job sets in **one pass** (one repo round-trip + one `xOnlyPublicKey` call instead of N+1) and returns `true` iff every signable input across all sets resolves to the baseline key — eligibility is monotonic so the union routes entirely to baseline iff every set does
- **BatchSignableIdentity one-popup path** *(restored in #535, originally #395)*: When `isBatchSignable(identity)` AND `InputSignerRouter.canBatch(arkTxJobs, ...checkpointJobs)` is `true`, `Wallet.buildAndSubmitOffchainTx` collapses the N+1 wallet popups (one arkTx + N checkpoints) into a single `identity.signMultiple(requests)` call. The N+1 → 1 optimization was silently lost when per-input routing moved into `InputSignerRouter` — `_signerRouter.sign` was called once per PSBT, never folding work across arkTx + checkpoints, so `signMultiple` was unreachable. **Send path**: user-signed arkTx + checkpoints are stashed; the unsigned checkpoints are submitted to arkd for its tapScriptSig; server + user sigs are merged via `combineTapscriptSigs` on each checkpoint (now with explicit input-count and per-input `tapScriptSig` invariants — rejects mismatches with input-indexed errors instead of silently appending `undefined` and corrupting the witness). A symmetric length guard rejects a server response carrying a wrong checkpoint count, mirroring the `signMultiple` return-length check. **Recovery path** (`finalizePendingTxs` batch fallback): hands `signMultiple` checkpoints that already carry the server's `tapScriptSig` and consumes the returned transactions directly — the `BatchSignableIdentity` interface contract was tightened to require implementations to preserve any pre-existing partial signatures and only ADD their own (a provider that drops the server sig would strand the tx in pending), so no `combineTapscriptSigs` merge is needed there. Mixed sends (arkTx non-batchable or a checkpoint missing a descriptor) fail fast at the unified `canBatch` call before `setPendingTxFlag` rather than mid-signing. Requests are deep-cloned (`tx.clone()`) before handing them to `signMultiple` so a misbehaving provider cannot mutate the originals before `submitTx`. HD / mixed-owner sends keep the sequential `_signerRouter.sign` path
- **waitForIncomingFunds**: One-shot helper now skips notifications carrying no incoming funds. `notifyIncomingFunds` also fires for purely outgoing activity — a `vtxo_spent` event carries `newVtxos: []` and an onchain tx that only spends from the boarding address yields empty `coins` — so the prior implementation could settle on the spent half of a self-send before the matching `vtxo_received` arrived, returning an empty result (flaky e2e "should finalize pending transactions"). Helper also tears down the subscription if the callback ran before the `notifyIncomingFunds` promise resolved, plugging a stop-handle leak
- **VTXOs**: Virtual transaction outputs managed off-chain via Ark protocol. Cache reconciliation is surgical: `IContractManager.refreshOutpoints(outpoints)` queries the indexer by outpoint, annotates with the owning contract's tapscripts, and upserts at the contract address (no cursor change, no full re-scan). `VtxoManager.revalidateBeforeSettle` pre-flights candidates against the indexer before submitting `renewVtxos` / `runPeriodicSettle` so stale-cache VTXOs are dropped silently rather than driving 60-second `VTXO_ALREADY_SPENT` retry loops. Persisted VTXOs are gated by owning script via `src/contracts/vtxoOwnership.ts` so legacy address buckets cannot leak wrong-script rows or win txid:vout dedup
- **Per-Call Renewal Threshold** *(0.4.30, closes #388)*: `IVtxoManager.renewVtxos(eventCallback?, options?)` now accepts a `RenewVtxosOptions` payload whose `thresholdSeconds` overrides the renewal threshold for that call only. Resolution order: `options.thresholdSeconds` → `SettlementConfig.vtxoThreshold` → `DEFAULT_RENEWAL_CONFIG.thresholdMs` (3 days); the manual API bypasses the `settlementConfig === false` gate. Validation runs before any state mutation — non-number, non-finite, or non-positive values throw `TypeError` (the override can arrive over the worker `MessageBus` so its type is not guaranteed at runtime, and a `0`/`<=100ms` threshold would silently revert to the 3-day default via the `isVtxoExpiringSoon` guard). `ServiceWorkerWallet.renewVtxos(eventCallback?, options?)` mirrors the new arg by attaching `options` as the `payload` of the `RENEW_VTXOS` request envelope; `RenewVtxosOptions` is re-exported from the package root
- **Per-Contract Tapscript Memoization** *(0.4.31, refs #521)*: `extendVirtualCoinForContract(vtxo, contractOrMap?, cache?)` accepts an optional `ContractTapscriptCache = Map<string, ContractTapscripts>` so the taproot tree (`forfeitTapLeafScript` / `intentTapLeafScript` / `tapTree`, all derived solely from `contract.params`) is built **once per distinct contract per annotation batch** instead of once per VTXO — `handler.createScript(contract.params)` was the dominant cost in `getVtxos()` / `getBalance()` on long spent/swept histories. `ContractManager.getVtxosForContracts` (the internal bulk-fetch + annotate path) instantiates a per-call cache before the `vtxos.map(...)` annotation. **Cache hits return cloned tapscripts**: a follow-up fix (`cloneTapLeafScript` / `cloneContractTapscripts`) deep-copies `controlBlock.internalKey`, `controlBlock.merklePath[]`, the leaf `script`, and `tapTree` (all `Uint8Array`s) per hit so concurrent PSBT-building callers can't mutate one VTXO's scripts and poison the cache. The no-cache branch is short-circuited (`if (!cache) return { ...vtxo, ...deriveContractTapscripts(contract) }`) so unbatched single-VTXO calls keep their original allocation profile. New public types `ContractTapscripts` and `ContractTapscriptCache` exposed from `src/wallet/utils.ts`
- **Boarding History De-duplication** *(0.4.31)*: `buildTransactionHistory` (`src/utils/transactionHistory.ts`) now suppresses the second history row that appeared whenever a settled boarding deposit also produced a leaf VTXO (the boarding `TxReceived` row and the batch-leaf `TxReceived` row both surfaced, double-counting the deposit). At the top of the build it snapshots the boarding receives (`allBoardingTxs.filter(isSettledBoardingReceive).sort((a, b) => a.createdAt - b.createdAt)`) into a mutable `unmatchedSettledBoardingTxs` list and consumes entries via the `consumeBoardingReceive(predicate)` helper as matching leaves are processed: (a) when a leaf's commitment **is** in `commitmentsToIgnore` (or its `settledBy` is), the matching boarding receive is consumed by `(commitmentTxid match OR settledBy match) AND createdAt ≤ vtxo.createdAt`; (b) when the leaf is **not** ignored and is not refreshed by another VTXO, a matching boarding receive is consumed by exact `amount` match (and createdAt window) and — if found — suppresses the would-be batch-leaf row. The companion fix populates `key.commitmentTxid` on `ReadonlyWallet`-built boarding `ArkTransaction` rows (`utxo.virtualStatus.commitmentTxIds?.[0] ?? ""`) so the (a) branch's commitment match has a non-empty key to compare against. The original guard also gained an `(!vtxo.settledBy || !commitmentsToIgnore.has(vtxo.settledBy))` clause so swept boarding deposits (where `settledBy` points at the ignored commitment) take the dedup branch rather than emitting a new row. **Ghost zero-amount sent fix** *(0.4.35, `40bf82f5`)*: `buildTransactionHistory` no longer records an offchain `TxSent` row when `txAmount === 0` and no assets move (`if (txAmount !== 0 || assets)` guard). A signer-rotation migration spends every VTXO to a single self output of the full amount, so `spentAmount === changeAmount` and the net sent is 0 — the old code emitted a confusing ghost zero-amount sent transaction. Zero-amount sends that DO move assets (issuance/reissuance/burn) are kept because `assets` is set in those cases
- **Ownership Gating**: `vtxoOwnership` helpers run at every contract-scoped read/write site; background sync writers warn-and-skip on unowned scripts, user-initiated wallet write paths throw. `updateDbAfterOffchainTx` / `updateDbAfterSettle` now group spent rows by owning script and route each bucket to its contract's address (multi-contract spends no longer collapse into the primary bucket); `getVtxosFromRepo` fails fast on undecodable wallet addresses (was silently zeroing balance). Since 0.4.25 (Tier 2 of #480), `WalletRepository` exposes optional script-scoped methods (`getVtxosForScript` / `saveVtxosForScript` / `deleteVtxosForScript`) implemented natively by all SDK backends (InMemory, IndexedDB, Realm, SQLite); `getVtxosForContract` / `saveVtxosForContract` dispatch helpers in `vtxoOwnership.ts` route to them when present and fall back to Tier 1 address-bucket + filter for custom backends. `VtxoRepositoryKey = { script; address? }` carries both keys (address still required by current backends)
- **Wallet Restore / Discovery** *(post-0.4.27, #492)*: `Wallet.restore({ gapLimit }: { gapLimit?: number } = {})` is an explicit gap-scan recovery entry point that rebuilds an HD wallet's contract set + VTXO cache from on-chain + indexer history alone. Implementation route: HD wallets (detected via `instanceof HDDescriptorProvider`, not duck-typing) drive `ContractManager.scanContracts({ deps, hd: true, gapLimit })`; non-HD wallets do a single static pass at index 0. `scanContracts` walks each registered handler that implements `Discoverable` (currently `DefaultContractHandler` + `DelegateContractHandler`), probing materialized descriptors via `HDDescriptorProvider.materializeDescriptorAt(i)` until `gapLimit` consecutive misses, capped at `SCAN_MAX_INDEX = 10_000` (hitting the ceiling without closing the gap window **throws** rather than silently truncating a fund-recovery scan, and bounds a buggy/malicious handler that returns unconditional hits). Each hit goes through a lighter `persistAndWatchContract` path that skips per-contract indexer pulls — the trailing `refreshVtxos({ includeInactive: true })` covers all scripts in one batched indexer call. After scan, `HDDescriptorProvider.advanceLastIndexUsed(maxHitIndex)` monotonically nudges the receive cursor (never backs off; the trailing `WalletReceiveRotator.pickActiveReceive` deterministically tiebreaks on the highest HD index when multiple `wallet-receive` contracts exist). Concurrent `restore()` calls coalesce — only the caller that actually starts the run gets its `gapLimit` validated; later callers join the in-flight promise and their `gapLimit` is silently ignored (documented in JSDoc). `dispose()` drains `_restoreInFlight?.catch(() => undefined)` before tearing down the contract/vtxo managers so a torn-down manager can't be called by `_runRestore`. The static descriptor for the non-HD branch is computed lazily (no `xOnlyPublicKey()` derivation for HD wallets where it would never be used). Discovery types and `scanContracts` options exported from the package root: `Discoverable`, `DiscoveryDeps`, `DiscoveredContract`, `isDiscoverable`, `ScanResult`, `ScanContractsOptions`, `HandlerError`. `WALLET_RECEIVE_SOURCE` source-of-truth declaration extracted to `src/contracts/metadata.ts` (dependency-free leaf) so `contracts/handlers/default.ts` can read it without re-importing from `wallet/walletReceiveRotator` — closes a `contracts → wallet` import cycle; the rotator still re-exports the constant for backward compatibility. `deriveDescriptorLeafPubKey` extracted to `identity/descriptor` so both the wallet rotator and the new contract-handler `discoverAt` implementations share the leaf-pubkey derivation path
- **Boarding Contract Type** *(post-0.4.32, updated post-0.4.33)*: `boarding` is now a first-class registered contract type with its own handler (`src/contracts/handlers/boarding.ts`, `BoardingContractHandler` + `BoardingContractParams = DefaultContractParams` exported from the package root). `BoardingContractHandler` shares the `DefaultVtxo.Script` shape with `default` and delegates `createScript` / `serializeParams` / `deserializeParams` / `selectPath` / `getAllSpendingPaths` / `getSpendablePaths` entirely to `DefaultContractHandler` — boarding semantics come from the contract type and from sourcing `csvTimelock` from the server's `ArkInfo.boardingExitDelay` (instead of `ArkInfo.unilateralExitDelay`), not from renamed params. Registered in `contracts/handlers/index.ts` alongside `default`/`delegate`/`vhtlc`; the smoke-dist post-build check expects `boarding,default,delegate,vhtlc`. - **btcd-Compatible Taproot Tree** *(0.4.34, ships with the @arkade-os/sdk@0.4.34 / @arkade-os/boltz-swap@0.3.39 release)*: `VtxoScript` now assembles its Taproot script tree using btcd's `txscript.AssembleTaprootScriptTree` algorithm rather than `@scure/btc-signer`'s `taprootListToTree` (a Huffman builder). Implementation faithfully reproduces btcd: **Phase 1** pairs leaves left-to-right (an odd trailing leaf is merged into the LAST branch built so far — NOT paired as a fresh leaf); **Phase 2** is a FIFO-queue merge (front two branches combine, push to back, repeat until one remains). `VtxoScript` consumes the new function and the obsolete odd-count `scripts.reverse()` workaround is removed. - **Capped Settlement / Renewal / Recovery VTXO Batches** *(0.4.34)*: `MAX_VTXOS_PER_SETTLEMENT = 50` (exported from `src/wallet/vtxo-manager.ts`) caps the VTXO-count payload of a single settlement to fit under arkd's intent tx-weight budget (`TX_TOO_LARGE`); boarding inputs are added uncapped. The cap is applied **after** purpose-specific sorting so the overflow that defers to a later cycle does not starve viable VTXOs: **recovery / manual settle** sorts by value descending (`byValueDescending`) so the capped subset has the best chance of clearing the dust threshold and carries the most value; **renewal / periodic settle** sorts by expiry ascending (`byExpiryAscending`) so the soonest-expiring VTXOs always make the cut (no missed renewal windows, no recovery livelock). Already-recoverable/expired VTXOs sort first under the expiry order; VTXOs with no batch expiry or a block-height-looking expiry value sort last. `runPeriodicSettle` short-circuits once the filtered set reaches the cap so cycle latency stays bounded. **Differentiated recovery error**: `recoverVtxos` no longer throws the same `No recoverable VTXOs found` for a genuinely empty wallet and a funded wallet whose highest-value sub-cap batch can't clear dust — the latter case now reports the cap, the recoverable count, and the dust threshold so operators can tell a stuck-but-funded wallet from an empty one (PR #549 review). `byValueDescending` and `byExpiryAscending` are pure (`[...vtxos].sort(...)`), input untouched. **Post-0.4.34 — settlement batches also capped by `vtxoMaxAmount`**: every settlement path now additionally respects the server's per-output ceiling `ArkInfo.vtxoMaxAmount` (`-1` = no limit sentinel) — each settlement path builds a single output equal to the (fee-adjusted) sum of its inputs and the server rejects any virtual output above `vtxoMaxAmount` with `AMOUNT_TOO_HIGH`, so capping the input total keeps the output within bounds and the overflow settles on the next cycle (mirroring the count-cap behaviour). New exported helper `capSettlementBatch<T extends { value: number }>(sorted, maxAmount: bigint)` selects inputs from a pre-sorted list under BOTH the `MAX_VTXOS_PER_SETTLEMENT` count cap (hard stop) and the amount cap — an input that would breach the amount bound is **skipped, not a stopping point**, so a smaller input behind an oversized one still gets in (a break would strand it and could leave the batch below dust); uses `> maxAmount` to mirror the server's strict check. The helper bounds each input's **gross** `value` (intentionally conservative — it has no fee context; the real output is smaller post-fee, so a batch that fits on gross always fits post-fee), while the fee-aware periodic-settle / manual-settle paths cap on the **net** (post-input-fee, and in `Wallet.settle` the projected post-output-fee) contribution instead — a deliberate, harmless asymmetry. Used by `recoverVtxos` (value-descending; differentiated below-dust error message now also names the `vtxoMaxAmount` limit) and `renewVtxos` (expiry-ascending; **warns** when VTXOs individually exceed the ceiling — those can never be renewed by this path and drift toward unilateral exit as expiry nears, so operators can act, e.g. split them; throws `No VTXOs available to renew within the per-output limit` when no batch fits at all — only reachable if the server lowered the ceiling below an existing VTXO). `runPeriodicSettle` and the no-params `Wallet.settle` path skip (don't stop at) VTXOs whose net contribution would push the running output total past the ceiling; in `Wallet.settle` boarding inputs are added uncapped but counted via the running total (if boarding alone exceeds `vtxoMaxAmount` no VTXO fits and the server rejects the over-limit output — a multi-output split is out of scope). New private `VtxoManager.getInfoProvider()` reads the optional `arkProvider` off the wallet for the `vtxoMaxAmount` lookup without requiring full boarding-sweep capability (`undefined` → treated as no limit)
